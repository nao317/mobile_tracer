## 1. 文書の目的と改訂履歴

MobilTracerは、車両の状態・整備・修理・引き渡しの記録を残し、関係者が同じ内容を確認・共有・検証するための事業者向け（BtoB）プロダクトである。本書は、三業態で使う共通基盤と、顧客ごとに構成する機能の要件を定める。導入候補者、提供側、開発担当者が対象範囲と受入条件を確認するための初期案であり、顧客との合意済み仕様ではない。

画面、API、DB、チェーンの詳細設計は本書の対象外とする。MarkdownからのPDF生成と手動共有は開発文書の運用であり、プロダクトの機能ではない。手順は `docs/README.md` に記載する。編集原本は本ファイルのみとし、PDFは各版の配布・参照用成果物とする。

### 根拠と確定度の読み方

- **資料**: `10_22中間発表.pdf`。ページ番号は表紙を含むPDFの物理ページを指す。画像内の文字も確認した。掲載された市場数値、料金、競合評価は外部資料で再検証していないため、採用判断の根拠にはしない。
- **指定**: 今回の依頼で定められた方針。資料と異なる場合はこちらを優先する。
- **追加提案**: 本書で具体化した動作・受入方法。レビューで変更できる。特に非機能の数値は契約上の保証値ではない。
- **仮定**: 初期案を成立させるための暫定条件。第13章に確認相手と確認事項を記載する。
- **未決**: 採用方式、契約、数値など、判断が残っている事項。未決であっても、企業間分離や未合意表示などの必須要件を免除しない。

機能要件の「根拠」は要件の由来を示す。指定だけでは決まらない例外処理や検証手順の細部は追加提案とする。P0はMVP必須、P1は導入先の検証後に追加、P2は将来候補を表す。P1・P2を含めて実装済みとは扱わない。

### 文書の責任と承認

編集の取りまとめは提供側の要件担当、業務の確認は各業態の顧客責任者、技術・運用条件の確認は提供側の技術責任者が担う案とする。担当者の氏名と実施日程は未割当であり、これらは承認済みの任命ではない。

| 確認対象 | 決定責任者の候補 | 承認に必要な証跡 | 現在の状態 |
| --- | --- | --- | --- |
| 共通基盤・MVPの範囲 | 提供側のプロダクト責任者 | 対象版、採否、残課題、決定日 | 未承認 |
| 業態別の流れ・共有・確認文面 | 導入顧客の業務責任者 | 対象業態、代表ケース、確認結果 | 未承認 |
| 検証・性能・復旧・保守 | 提供側の技術責任者 | 方式、試験条件、測定結果、提供条件 | 未承認 |

文書は `draft` からレビュー中の `in-review` を経て、上記の確認を記録した場合だけ `approved` とする。文書の自動検査やAIによる品質レビューは、人の承認や製品受入を代行しない。承認前は0.x版を維持する。

### スキルの適用と既存文書への合わせ方

要件の品質点検にはMicrosoft HVE-Coreの `requirements-author` を使用し、目標、検証条件、追跡可能性、未決事項を補った。スキルのPRDテンプレートの内容を、本書の既存13章へ対応付けている。元のFR・NFR・ACは参照を壊さないため採番を変更せず、新設するGOAL・CON・DD・OQは3桁とする。既存IDを能力のまとまりとして保持し、個別の実装チケットと同一視しない。

Marpの説明内容整理は別の派生文書とし、本書を要件の編集原本として維持する。適用したコミット、出典、書式の適用差分は `docs/skill-sources.md` に記録する。スキルの全テンプレートへの完全準拠や、規格への認証を意味しない。

## 2. 記録の偏りを減らし、車両の履歴を確認できるようにする

発表資料は、レンタカー返却時の傷をめぐり、利用者が貸出前の状態を後から示しにくい課題を挙げている（資料p.2、4）。状態と整備履歴の蓄積、関係者間の共有、改ざん検証、AIによる確認支援を解決の方向としている（資料p.5〜6）。整備履歴を車両ごとに積み上げ、売買時の確認や外部サービスとの連携に広げる構想もある（資料p.9）。

本書では、レンタカー・カーシェア、販売店、個人事業者を含む整備・修理業者を顧客として想定する（指定）。共通する「状態を記録する→提示する→確認する→後から比較・検証する」業務を支え、必要な機能だけを組み合わせて顧客に提供する。

| 主体 | 提供価値 | MVPで確かめること |
| --- | --- | --- |
| 顧客 | 受付・引き渡し時の確認漏れを減らし、経緯を説明できる | 三業態で同じ記録基盤を使い、業務別の設定で流れを変えられる |
| 利用者・所有者 | 提示された内容と自分の回答を後から確認できる | 未同意・異議も含む履歴を、案内された方法で閲覧できる |
| 提供側 | 共通基盤を保守しながら顧客別に構成できる | 他社や確定記録を変えずに設定を更新できる |

改ざん検証は、登録時点から内容が変わっていないかを確かめる機能である。写っていない傷、撮影前の偽装、撮影日時の真実性、当事者の共謀、傷を付けた責任、修理費の妥当性までは証明しない（指定、資料p.13）。資料p.6の証拠を保証する表現を、法的効力の保証として採用しない。資料p.14でも証拠能力は未確認とされている。

### GOAL-001 三業態で共通基盤の有効性を確かめる

- 目標: MVPの受入時に、三業態それぞれの代表フローを、共通の車両・案件・記録基盤と設定で完了する。
- 指標: AC-01で完了した業態数／対象の三業態。
- 基準値: 未計測。製品未実装のため、0件という実測値には置き換えない。
- 目標値: 3／3業態。元の依頼に基づく受入目標。
- 測定方法: 各業態の架空案件を一件以上実行し、使用した構成版と完了した段階を記録する。
- 測定期間: MVP受入の開始から合否判定まで。実施日は未定。
- 判定責任者: 提供側のプロダクト責任者を候補とし、各業態の顧客責任者が業務結果を確認する。
- 達成可能性: 実装規模・予算・日程は未評価。実現済みと判断しない。

### GOAL-002 提示記録と本人の意思表示を後から追跡できる

- 目標: MVPの受入時に、提示した版、確認文面、回答、訂正、異議の対応を再構成できる。
- 指標: AC-02、AC-03、AC-06、AC-09の必須ケースのうち、対象版と本人の回答を取り違えずに再確認できたケース数／実施ケース数。
- 基準値: 未計測。
- 目標値: 必須ケース100%。署名拒否・無回答を合意として扱ったケースは0件。
- 測定方法: 画面と本人控えを照合し、対象版・確認種別・回答・公開範囲を判定票に記録する。
- 測定期間: MVP受入時。期限切れ・訂正後の再閲覧を含める。
- 判定責任者: 導入顧客の業務責任者を候補とする。
- 達成可能性: 本人確認と控えの方式・保存条件はOQ-001、OQ-003、OQ-006で決定する。

### GOAL-003 登録後の変更と検証できない状態を判別できる

- 目標: MVPの受入時に、原本の不変、差し替え、基準不足、原本欠落を区別し、検証状態を説明できる。
- 指標: AC-04、AC-08、AC-10の必須検証ケースで、事前に定めた期待結果と照合結果が一致したケース数／実施ケース数。
- 基準値: 未計測。
- 目標値: 必須ケース100%。検証不能を一致と表示するケースは0件。
- 測定方法: 改変前後の原本、独立基準、登録状態、照合結果を比較する。責任や真実性の判定は測定対象に含めない。
- 測定期間: MVP受入時。登録失敗・再起動・復元後の確認も行う。
- 判定責任者: 提供側の技術責任者を候補とする。
- 達成可能性: 独立基準・鍵・登録先の方式をOQ-002で決定し、実環境での実証を要する。

### GOAL-004 顧客別構成を分離して提供・保守できる

- 目標: MVPの受入時に、顧客別の設定変更、権限変更、導入・サポート作業を、他社や確定記録を変えずに行う。
- 指標: AC-05、AC-07、AC-16の必須ケースで発生した、他社データの参照・変更、確定記録の変更、期限外サポートアクセスの件数。
- 基準値: 未計測。
- 目標値: 上記の不正な参照・変更・アクセスは0件。通知等の有効性はAC-16のケース別に判定する。
- 測定方法: 二顧客以上の環境で設定・共有・サポート操作を行い、変更前後と操作履歴を照合する。
- 測定期間: MVP受入時と共通基盤更新時の回帰確認。
- 判定責任者: 提供側の運用責任者を候補とする。
- 達成可能性: 構成の移行条件、担当権限、サポート契約をOQ-005、OQ-007で合意する。

これらは測定可能な受入目標であり、実績値や顧客合意済みKPIではない。日程・予算・責任者の任命がないため、SMARTの達成可能性と期限の合意は残る。売上増加や紛争削減率を、根拠のない数値で追加しない。

| 用語 | 定義 |
| --- | --- |
| 顧客 | MobilTracerを導入する事業者。企業・個人事業者の双方を含む |
| 利用者 | 顧客からサービスを受ける借受人、購入者、修理依頼者など |
| 提供側 | MobilTracerを構築・提供・保守する主体 |
| 利用環境 | 顧客のデータ・構成・権限を分離して管理する単位。以下、テナントとも呼ぶ |
| 車両 | ナンバーに依存しない内部識別子を持つ管理対象 |
| 案件 | 一回の貸出、修理、販売などの業務単位。主対象の車両を一台持つ |
| 記録・記録版 | ある時点の写真・点検結果等をまとめた記録と、その内容を識別する版 |
| 提出・確定 | 担当者が提示対象の記録版を変更不可として保存すること。双方の同意とは別 |
| 合意 | 特定の当事者が特定の記録版・確認事項に明示的に同意すること |
| 署名 | 回答者、対象版、確認の意味、日時を結びつけた意思表示。暗号署名の方式は未決 |
| ハッシュ | ファイルや記録の内容から算出する照合値。内容変更の検出に用いる |
| 検証基準 | 提出時の照合値を、通常の記録編集とは別に保全した情報 |
| チェーン登録 | 検証基準をブロックチェーン等へ登録する処理。業務完了とは別の状態を持つ |
| 共有・本人控え | 期限・範囲付きの閲覧許可と、本人に提示した記録版・回答の保存用控え |

| 利用主体 | 主な役割・責任 |
| --- | --- |
| 提供側管理者 | 利用環境、提供機能、運用権限を管理する。顧客記録の自由閲覧権を持たない |
| 提供側導入担当者 | 契約された範囲でテンプレート、設定、データ取り込みを支援する |
| 提供側サポート担当者 | 顧客が許可した範囲と期間だけ調査する。自己判断で閲覧範囲を広げない |
| 導入企業の管理者 | 顧客内の店舗・担当者・権限・設定・共有方針を管理する |
| 店舗責任者 | 担当店舗の案件、承認、未対応事項を管理する |
| 受付・販売・整備等の担当者 | 割り当てられた案件の記録、提示、作業、引き渡しを担当する |
| 所有者・借受人・購入者・修理依頼者 | 関係する案件の提示記録を確認し、回答・異議を残す。所有者が常に利用者とは限らない |
| 外部関係者 | 保険会社、別事業者等。個別に許可された記録だけを確認する |

同じ人が所有者と修理依頼者を兼ねる場合や、個人事業者が企業管理者・店舗責任者・担当者を兼ねる場合を認める。権限は人に一役だけ割り当てる前提にしない。兼務しても、どの資格で何を行ったかを記録する。職務分離が必要な顧客では、同一人物による作成・承認を禁止する設定を適用する（追加提案）。

## 4. 対象は車両業務の記録・共有・確認・検証

初期の汎用化範囲は車両関連業務とする。スマートフォンのブラウザーを主な記録手段とし、管理業務はPCでも行う想定である（仮定）。顧客内の複数店舗、個人事業者の一店舗、案件ごとの複数関係者に対応する。

| 区分 | 含む内容 |
| --- | --- |
| MVP | 共通基盤、三業態の最小テンプレート、顧客別設定、写真・点検、比較、提出、共有、確認・署名、異議、追記、改ざん検証、監査、最低限の提供側運用 |
| 段階的に拡張 | 動画、まとまった移行支援、外部連携、高度な承認、AI支援。詳細は第11章 |
| 対象外 | 予約、決済、会計、在庫、部品発注、保険査定、責任割合や請求額の自動決定、法的効力の保証 |
| 将来構想 | 車両以外への適用。他領域の情報構造や規制への対応は今回確定しない |
| 今回の作業対象外 | プロダクト本体の実装、Google Driveへの接続・認証・探索・アップロード・自動共有 |

既存READMEにはReact Router、Go、PostgreSQL、Tapyrus等の構成方針がある。本書では業務要件をそれらに従属させず、Tapyrusも検証手段の技術候補とする（指定）。既存方針との差異は第13章で採用判断を行い、READMEを黙って変更しない。

### 外部から指定された制約

| ID | 区分・指定元 | 境界と変更条件 |
| --- | --- | --- |
| CON-001 | 業務範囲。本依頼 | 初期の汎用化は車両業務に限定する。車両以外への拡張には対象領域の要件を再確認する |
| CON-002 | リリース範囲。本依頼 | 予約・決済・会計・在庫・部品発注を自動的にMVPへ追加しない。追加には依頼者による対象範囲の変更が必要 |
| CON-003 | 提供構成。本依頼 | 顧客別のコード複製を基本方式にしない。設定・モジュール・拡張の境界を守り、例外は提供側の保守責任と費用を合意する |

制約は機能の受入条件や非機能の提案値と区別する。今回の作業範囲である「製品本体を実装しない」「Markdown原本・PDF生成」「Driveへのアップロードは手動」も継続するが、製品が利用者へ提供する機能とは扱わない。

## 5. 共通基盤を更新しながら顧客別に構成する

### 三層の提供方針

| 層 | 内容 | 変更の扱い |
| --- | --- | --- |
| 共通基盤 | 組織、権限、車両→案件→記録、状態記録、比較、提出、確認、検証、履歴、共有、異議、通知、出力、監査 | 全顧客で共通の不変条件を守る。機能の有効化で情報分離・追記原則・監査を無効にできない |
| 業務モジュール | 貸出・返却、仕入・納車、入庫・承認・作業・引き渡し | 共通の記録と承認機能を使い、業務の用語・段階・専用項目を加える |
| 顧客別設定・拡張 | 利用機能、項目・必須条件、撮影箇所、点検、段階と移行条件、承認者・順序、通知・期限、用語、ロゴ・帳票、連携 | 顧客別の構成版として管理し、試行後に適用範囲を指定して反映する |

### 標準・設定・追加モジュール・個別開発の境界

| 区分 | 判断基準 | 例・制約 |
| --- | --- | --- |
| 標準機能 | 業態を問わず必要で、記録の信頼性を支える | 提出版の保存、未合意表示、権限判定、検証結果、監査 |
| 設定で対応 | 共通のデータ・権限・状態の意味を変えずに表現できる | 撮影箇所、チェック項目、承認順、期限、用語、ロゴ。8方向撮影と24時間の異議受付は初期候補 |
| 追加モジュール | 複数顧客で再利用できる業務能力や連携が必要 | 追加作業の承認、業界向け連携。標準の履歴・権限・検証を利用する |
| 個別開発 | 設定・既存モジュールで表せず、一顧客固有の業務がある | 専用の外部接続など。影響、費用、保守責任、更新追随を合意して追加する |

個別開発の前に、設定での表現可否、複数顧客での再利用性、機密情報への影響、更新時の互換性、運用費用を確認する。顧客ごとのコード複製を基本方式にしない。拡張によって提出済み内容や署名の意味を変更できる構成は採用しない。

### 設定更新の影響範囲

新規案件は開始時の構成版を参照する。進行中案件は原則として開始時の版を維持し、管理者が差分・入力不足・承認への影響を確認した場合だけ、下書きと将来の業務段階を移行できる。移行で追加された必須項目は、該当段階の次回提出前に入力する。既に提出した記録版、提示内容、署名には遡及しない（追加提案）。

テンプレートの更新は顧客への提案として配布し、自動で本番設定を置き換えない。ある顧客への反映やロールバックは他社に影響しない。過去の構成版は、その版で作成された記録を表示する間保持する。設定の巻き戻しも新しい構成版として残し、確定記録を巻き戻さない。

## 6. 三業態の代表的な業務フロー

共通の準備は、利用環境とテンプレートの作成（FR-T01）、機能・項目・業務段階の設定（FR-T02）、試行と本番反映（FR-T03）、担当者の権限付与（FR-C01）である。以下の「確認」では、閲覧・受領・状態同意・作業承認のどれを求めるかを明示する。

## 7. 機能要件

### FR-C01 組織・店舗・担当者・権限を管理する

- 利用主体: 導入企業管理者、店舗責任者、提供側管理者。
- 開始条件: 顧客管理者が担当者の招待・役割付与・停止を操作したとき。
- 目的: 顧客と店舗の境界を守り、兼務を含めて担当範囲を定める。
- 動作: テナント、店舗、担当者、役割、対象範囲を管理する。招待・停止・権限変更を記録し、複数役割を付与できる。提供側の運用権限と顧客データへのアクセス権を分ける。
- 例外: 最後の企業管理者の停止を防ぎ、退職者の新規アクセスを停止する。既存記録の作成者・署名者情報は消さない。
- 適用範囲: 共通基盤、全業態。
- 優先度: P0。
- 受入条件: 一人に管理と記録の役割を付与できる。他店舗・他社の直接URL参照と更新を拒否し、停止済み担当者のセッションを無効化できる。
- 根拠: 指定。最後の管理者保護と停止の具体動作は追加提案。

### FR-C02 ナンバーが変わっても車両を追跡する

- 利用主体: 担当者、店舗責任者。
- 開始条件: 担当者が車両を登録・照合し、またはナンバー・所有者の変更を登録したとき。
- 目的: ナンバーや所有者の変更で履歴を分断しない。
- 動作: 車両に不変の内部識別子を付ける。車台番号等の識別情報とナンバー・所有者の有効期間を管理し、検索・照合できる。未確認の識別情報は確認済みと区別する。
- 例外: 車台番号不明でも仮登録を認め、後で照合する。重複候補は権限者が確認し、関連付け・統合の経緯を残す。統合しても提出版の車両表示を変更しない。
- 適用範囲: 共通基盤、全業態。
- 優先度: P0。
- 受入条件: 同じ車両のナンバー・所有者変更後も、許可された過去案件を内部識別子で参照できる。同じナンバーを持つ別車両を自動統合しない。
- 根拠: 指定、資料p.9の車両単位の履歴。仮登録・統合手順は追加提案。

### FR-C03 車両に案件と関係者を関連付ける

- 利用主体: 担当者、店舗責任者。
- 開始条件: 担当者が業務案件を開始し、関係者を関連付け、または案件を中止したとき。
- 目的: 一回の業務に属する記録と当事者をまとめる。
- 動作: 主対象の車両、案件種別、担当店舗・担当者、関係者、業務段階、開始時の構成版を指定する。関係者には所有者・依頼者・承認者などの資格と関与期間を設定する。
- 例外: 同じ車両の並行案件を区別する。案件中止は理由を残し、提出記録を削除しない。関係者の追加だけで過去の共有権限を付与しない。
- 適用範囲: 共通基盤、全業態。
- 優先度: P0。
- 受入条件: 車両から案件別の記録をたどれ、同じ車両の別案件へ回答や写真が混入しない。
- 根拠: 指定。案件中止・並行案件の扱いは追加提案。

### FR-C04 写真・点検結果などの状態を記録する

- 利用主体: 担当者、許可された利用者。
- 開始条件: 権限のある人が撮影・添付・点検入力を行い、保存または再送したとき。
- 目的: 入出庫や引き渡し時点の状態を具体的に残す。
- 動作: 原本写真、傷の位置・説明、点検結果、付属品、燃料、走行距離、自由記述を記録する。写真に撮影者、端末申告の撮影日時、サーバー受信日時を保持する。注釈・加工画像は原本と関連付けた別データとし、加工の種類を表示する。動画も段階的に扱う。
- 例外: 読み取れない画像、容量超過、送信中・失敗を示す。位置情報は任意かつ目的を明示し、取得不能を偽装扱いしない。送信再試行で同じ写真を重複登録しない。
- 適用範囲: 共通基盤。利用者による投稿は案件・項目単位で許可する。
- 優先度: P0（写真・点検・原本管理）、P1（動画）。
- 受入条件: 注釈を外して原本を確認できる。時刻の出所を区別し、端末時刻がずれてもサーバー受信日時を保持する。未送信写真を提出済みと表示しない。
- 根拠: 指定、資料p.7〜8、13。時刻と再送制御の細部は追加提案。

### FR-C05 撮影・点検を案内し、入力漏れを示す

- 利用主体: 担当者、記録を投稿する利用者。
- 開始条件: 記録作成を開始し、撮影・点検項目を進め、または提出を要求したとき。
- 目的: 必要な箇所を同じ基準で記録できるようにする。
- 動作: 顧客設定に従って撮影箇所、参考画像、点検項目、必須項目、未完了項目を表示する。資料の8方向撮影はテンプレートの初期候補として選択できる。
- 例外: 撮影不能は理由を記録し、設定で許可された責任者だけが不足を承認できる。不足承認を正常な撮影完了と同じ表示にしない。
- 適用範囲: 共通基盤、顧客別設定。
- 優先度: P0。
- 受入条件: 6箇所と8箇所の設定を別顧客に適用でき、必須不足時には該当項目を示して提出を止める。例外承認を使った場合は理由と承認者が残る。
- 根拠: 指定、資料p.7〜8。撮影不能時の扱いは追加提案。

### FR-C06 異なる時点の状態を比較する

- 利用主体: 担当者、共有を受けた利用者・外部関係者。
- 開始条件: 権限のある人が同じ車両の二つの記録版と撮影箇所を選択したとき。
- 目的: 貸出前後、入庫・作業後、納車前後の変化を確認する。
- 動作: 対象とする二つの記録版と撮影箇所を指定し、写真・傷・点検・備品等を並べて表示する。差分について担当者の判定と根拠を残す。
- 例外: 同じ箇所の写真がない、撮影条件が違う、片方の閲覧権限がない場合は比較不能の理由を示す。欠落を「変化なし」にしない。
- 適用範囲: 共通基盤、全業態。
- 優先度: P0。
- 受入条件: 対象版を表示したまま比較でき、片方の共有権限を外すと当該写真は表示されない。人の判断と画像上の候補を区別できる。
- 根拠: 指定、資料p.7〜8。

### FR-C07 相手の署名がなくても提出版を保存する

- 利用主体: 記録作成者、提出権限を持つ担当者。
- 開始条件: 提出権限を持つ担当者が保存済み下書きの提出を要求したとき。
- 目的: 提示時点の内容を、相手の回答の有無に左右されず残す。
- 動作: 下書きの入力・添付完了を確認し、提出操作で内容・添付原本・構成版・提出者・提出日時・照合値を固定する。保存完了後に提示可能とし、合意状態を別に管理する。
- 例外: 同時編集は競合を知らせ、古い下書きによる上書きを拒否する。提出処理の再送は同じ提出結果を返す。必須不足・添付失敗時は提出しない。
- 適用範囲: 共通基盤、全業態。
- 優先度: P0。
- 受入条件: 署名拒否・無回答の案件でも提出版と提示対象の内容を再閲覧できる。提出後の直接更新は、提供側を含めて拒否される。
- 根拠: 指定。資料p.8、11、13の双方署名を記録追加の条件とする方針から変更。合意がなくても提出と検証基準の保存を行う。

### FR-C08 確認の意味と対象版を指定して回答を残す

- 利用主体: 利用者、所有者、権限を持つ担当者・承認者。
- 開始条件: 対象版の提示を受けた人が確認種別を選び、回答または署名したとき。
- 目的: 何を確認・承認したのかを後から判別できるようにする。
- 動作: 閲覧、受領、状態への同意、作業承認を区別して表示する。回答者、本人確認手段、資格、対象記録版、確認文面の版、承認対象の範囲・金額、回答・署名、時刻を保存する。提示版と自分の回答を本人控えとして後から閲覧・取得できる。
- 例外: 拒否、保留、無回答、期限超過を明示する。期限超過を同意に変更しない。代理回答は代理の資格と権限確認を残し、本人回答に見せない。記録・見積変更後は新しい回答を求め、旧版の署名を流用しない。
- 適用範囲: 共通基盤。承認順序は顧客設定。
- 優先度: P0。
- 受入条件: 受領だけを回答した人を状態同意済みにしない。旧版に署名した後、新版には未回答と表示される。署名しない人にも提示済み版を保存用に取得する手段を案内する。
- 根拠: 指定、資料p.7〜8の署名。本人確認方式、本人控えの提供方法は追加提案・未決。

### FR-C09 提出後の変更を検証する

- 利用主体: 権限のある関係者、提供側運用担当者。
- 開始条件: 対象版の閲覧権限を持つ人が登録内容の照合を実行したとき。
- 目的: 登録された原本や記録内容の差し替えを検出する。
- 動作: 提出版・原本のハッシュを、独立して保全した検証基準と照合する。対象、方式、照合日時、基準の登録状態を添えて、一致・不一致・検証不能を表示する。記録版の内容と添付原本の対応も検証対象にする。
- 例外: 写真削除、取得失敗、基準不足、未登録、未対応方式は検証不能とし、一致扱いにしない。注釈画像の変更と原本の変更を区別する。
- 適用範囲: 共通基盤。チェーンの製品選定とは独立した業務要件。
- 優先度: P0。
- 受入条件: 検証環境で登録済み写真のバイト列を一枚差し替えると不一致になる。原本と通常DBの照合値を同時変更しても、独立基準との不一致を検出する。真実性や責任の証明と説明しない。
- 根拠: 指定、資料p.9、11の差し替え検出、p.13の限界。

### FR-C10 チェーン等への登録状況と再試行を管理する

- 利用主体: 提供側運用担当者、店舗責任者、確認する関係者。
- 開始条件: 提出版の検証基準を外部保全へ送信し、結果を照会し、または再試行するとき。
- 目的: 外部登録の遅延・障害を業務完了や合意と混同しない。
- 動作: 検証基準の登録を未登録・登録待ち・送信中・結果未確定・登録済み・失敗で管理し、送信履歴と参照情報を残す。再試行前に結果を照会して二重登録を防ぎ、停滞を通知する。再起動後も登録待ちを引き継ぐ。
- 例外: 通信失敗や応答喪失でも提出版を失わない。未完了時は「登録済み」「検証済み」と表示しない。顧客が続行を認める段階でも未完了表示を残す。
- 適用範囲: 共通基盤。Tapyrusは候補。MVPは少なくとも一方式で独立基準への登録と実照合を実証する。
- 優先度: P0。
- 受入条件: タイムアウト、登録成功後の応答喪失、処理再起動を試験し、同一記録の登録先を追跡できる。双方署名がなくても未合意の提出版を検証対象として保持する。
- 根拠: 指定、資料p.7〜9。登録状態・再試行方法は追加提案。

### FR-C11 確定記録は元版を残して訂正・補足する

- 利用主体: 訂正権限を持つ担当者、確認者。
- 開始条件: 権限のある担当者が提出済み版への訂正・補足を要求したとき。
- 目的: 誤記の訂正と過去の提示内容の保全を両立する。
- 動作: 提出版に、訂正・補足の区分、理由、対象箇所、作成者、新版または追記を関連付ける。元版と差分を閲覧でき、必要な相手に再確認を依頼する。
- 例外: 過去版の削除・上書きで訂正しない。異議の解決や管理者操作によっても旧署名を新内容へ移さない。削除が必要な場合は保存方針に従う別手続きとする。
- 適用範囲: 共通基盤、全業態。
- 優先度: P0。
- 受入条件: 燃料値の訂正後、元の値・署名・提示時点と新しい値・未回答状態を区別して表示できる。
- 根拠: 指定。

### FR-C12 範囲・期間・相手を指定して共有する

- 利用主体: 共有権限を持つ顧客管理者・担当者、共有先の関係者。
- 開始条件: 共有権限を持つ人が相手・版・項目・期間を指定し、共有または取消しを実行したとき。
- 目的: 必要な情報だけを共有し、提示した版を追跡する。
- 動作: 相手、目的、対象記録版、公開項目、マスキング、閲覧・取得の可否、期限を指定する。共有前に公開内容をプレビューし、認証等で相手を確認してアクセスさせる。取消しと期限切れは以後のアクセスに反映する。
- 例外: 推測できるURLだけで個人情報を公開しない。取消し後の既存セッションや直接添付URLも拒否する。ダウンロード済みの控えは遠隔削除できないことを共有時に示す。
- 適用範囲: 共通基盤。社内、利用者、他事業者、所有者への共有。
- 優先度: P0。
- 受入条件: 指定した写真と点検だけを外部関係者が閲覧でき、内部メモ・過去利用者情報・別案件は取得できない。取消し後の再読込を拒否する。本人控えとの関係は第8章に従う。
- 根拠: 指定、資料p.5〜6、12の双方共有。認証・マスキングの細部は追加提案。

### FR-C13 異議・差し戻し・再確認の経緯を残す

- 利用主体: 利用者、所有者、承認者、担当者、店舗責任者。
- 開始条件: 関係者が対象版への異議・差し戻しを行い、担当者が再確認を依頼したとき。
- 目的: 合意できない点と対応の責任を明確にする。
- 動作: 異議の対象記録版・項目、申出者、内容、証拠、受付日時、担当、対応、再確認の回答を残す。内部の差し戻しは利用者の異議と区別する。
- 例外: 期限内の申出は端末操作時刻だけでなく受信時刻で判定する。通信断の申出は事情と時刻を保全し、期限後の申出として責任者へ回せる。受付期限後も申出を消さず、受付可否と理由を残す。解決操作は相手の同意を自動生成しない。
- 適用範囲: 共通基盤。期限・起算イベント・受付後の担当は顧客設定。
- 優先度: P0。
- 受入条件: 24時間と48時間の設定を使い分けられる。無回答の期限到来後も未回答のままとし、異議と元記録を併せて追跡できる。
- 根拠: 指定、資料p.7〜8の24時間は初期候補。期限後対応の細部は追加提案。

### FR-C14 通知と未対応事項を管理する

- 利用主体: 担当者、責任者、利用者、提供側運用担当者。
- 開始条件: 確認依頼・承認待ち・異議・登録失敗が発生し、通知または担当変更を行うとき。
- 目的: 確認依頼、承認待ち、異議、登録失敗の放置を防ぐ。
- 動作: 担当者・期限を持つ未対応一覧を表示し、設定した契機で通知する。MVPは画面内一覧と確認依頼の通知手段を少なくとも一つ提供する。配信状態と業務上の回答状態を別管理する。
- 例外: 通知失敗を残して再送できる。メール等への到達・リンクの開封を合意にしない。通知本文に不要な個人情報や画像を含めない。
- 適用範囲: 共通基盤。通知先・期限・再通知は顧客別設定。
- 優先度: P0（一覧・基本通知）、P1（複数経路・高度なエスカレーション）。
- 受入条件: 未回答の依頼と検証登録失敗が一覧に残り、担当変更後も重複処理や未対応事項の消失が起きない。
- 根拠: 指定。通知経路は未決。

### FR-C15 帳票・データ・本人控えを出力する

- 利用主体: 担当者、管理者、提示を受けた本人。
- 開始条件: 権限のある人が対象版と公開範囲を選び、帳票・データ・控えの出力を要求したとき。
- 目的: 提示内容や対応経緯をシステム外でも確認できるようにする。
- 動作: 選択した記録版、写真、回答、署名の意味、異議、検証状況を帳票に含める。管理者は許可された範囲を機械可読形式でも出力できる。出力日時、対象版、公開範囲を表示する。
- 例外: 未合意の記録に「双方確認済み」を表示しない。権限外の情報やマスク前の画像を出力しない。画像削除・検証未完了・履歴の非掲載範囲を隠さない。
- 適用範囲: プロダクトの帳票・データ出力。開発文書のPDFビルドとは別機能。
- 優先度: P0（標準帳票・本人控え・基本データ出力）、P1（顧客独自レイアウト）。
- 受入条件: 署名拒否を含む案件の提出版と本人の回答を出力でき、画面と帳票で合意・検証の表示が一致する。
- 根拠: 指定、資料p.14の運営停止時の備え。出力項目は追加提案。

### FR-C16 操作とアクセスの履歴を保存する

- 利用主体: 顧客管理者、監査権限者、許可された提供側担当者。
- 開始条件: 監査対象の操作・アクセスが発生し、または監査権限者が履歴を検索したとき。
- 目的: 誰が何を参照・変更・提供したかを調査できるようにする。
- 動作: 認証、権限変更、記録提出、回答、訂正、共有・取消し、出力、削除、設定反映、サポートアクセスを、実行者・対象・時刻・結果・代理資格とともに残す。対象を絞って検索・出力できる。
- 例外: 通常の管理者操作で履歴を書き換えられない。パスワード、認証トークン、不要な画像・個人情報をログ本文に残さない。提出・署名等は監査情報を永続化できるまで成功としない。
- 適用範囲: 共通基盤、提供側運用を含む。
- 優先度: P0。
- 受入条件: 一件の共有取消しとサポート閲覧を実行者まで追跡できる。顧客は他社の操作履歴を取得できない。
- 根拠: 指定。履歴項目と保存失敗時の扱いは追加提案。

### FR-C17 記録の継続保存と個別の削除手続きを管理する

- 利用主体: 顧客管理者、提供側運用担当者。
- 開始条件: 記録の保存、削除申請、契約終了、または削除済みデータを含む復元が発生したとき。
- 目的: 車両の履歴と検証可能性を維持し、個別に削除が必要な場合は判断と実行の経緯を残す。
- 動作: 写真、記録、本人控え、共有情報、監査履歴は継続保存を基本とし、期間経過による自動削除は行わない。契約終了時の出力、個別の削除申請、理由・対象・承認・実行結果を管理し、異議対応中の保留を扱う。共有期限はアクセス許可の期限として扱い、記録の削除条件にしない。
- 例外: 承認された個別の削除で原本を消した後は検証不能と表示し、削除理由・実施日時等の最小履歴を残す。バックアップ内の削除対象は復旧時にも削除を再適用する。チェーン上の値を消去できると約束しない。
- 適用範囲: 共通基盤。個別の削除条件、保留根拠、契約終了・バックアップの扱いは契約前に確認する。圧縮・アーカイブは今回の対象外とする。
- 優先度: P0（継続保存の方針・個別の承認付き削除運用）。
- 受入条件: 過去の作成日時の記録と原本が期間経過だけでは削除されず、共有期限が切れても保持される。個別の削除申請では理由・承認・実行結果が残り、原本消去後に「一致」と表示されない。
- 根拠: 指定（期間経過による自動削除を行わず、圧縮は後回しとする方針）。削除手続き・バックアップへの再適用は追加提案。

### FR-C18 履歴蓄積と所有者・事業者間共有を分ける

- 利用主体: 所有者、顧客管理者、販売担当者、共有先事業者。
- 開始条件: 所有者を変更し、または車両履歴を他事業者・新所有者へ共有するとき。
- 目的: 車両履歴を活用しながら、過去の当事者の情報を保護する。
- 動作: 所有者の有効期間と履歴の公開許可を別管理する。事業者間は送信側の承認と受信側の受入れを経て、出所・対象版・共有条件を持つ履歴として扱う。購入者向けには個人情報を除いた履歴を選択する。
- 例外: 所有者変更や車台番号の一致だけでは、他社の履歴・過去の利用者情報を公開しない。誤移転は共有を止めて経緯を残す。共有取消し後も受信側に取得済みの帳票まで消せるとは扱わない。
- 適用範囲: 共通基盤。MVPでは手動承認による限定共有とマスキングを実証する。
- 優先度: P0（選択共有・所有者変更時の保護）、P1（継続的な事業者間連携）。
- 受入条件: 所有者を変更しても旧借受人の氏名・連絡先・署名は新所有者に表示されず、許可した整備事実だけを共有できる。
- 根拠: 指定、資料p.9の整備・売買への活用。移転手順は追加提案。

### FR-M01 貸出・返却を共通記録で扱う

- 利用主体: 貸出担当者、店舗責任者、借受人。
- 開始条件: 顧客が貸出・返却モジュールを有効にし、担当者が貸出案件を開始したとき。
- 目的: レンタカー・カーシェアの前後確認を支える。
- 動作: 貸出前確認、貸出、返却確認、完了の段階を用意し、燃料・距離・備品・状態の記録、比較、回答を共通基盤に関連付ける。
- 例外: 備品不足、燃料差、署名拒否、異議を残したまま担当対応に回せる。金額や責任は自動確定しない。
- 適用範囲: レンタカー業務モジュール。予約・決済は含まない。
- 優先度: P0（代表フロー）。
- 受入条件: 第6章の貸出から返却までを共通の記録・確認機能で実行し、燃料・距離・備品の差分を表示できる。
- 根拠: 指定、資料p.2、7〜8。

### FR-M02 仕入・整備・履歴共有・納車を扱う

- 利用主体: 仕入・販売・整備担当者、購入者、所有者。
- 開始条件: 顧客が販売店モジュールを有効にし、担当者が仕入・下取案件を開始したとき。
- 目的: 販売前の状態と納車時の確認を説明できるようにする。
- 動作: 仕入・下取、整備、購入前共有、納車確認を設定し、各段階の状態・整備記録を関連付ける。購入者へは選択した履歴を公開し、納車版の受領・同意を得る。
- 例外: 出所不明の履歴は確認済みと表示しない。非共有の整備記録や過去利用者情報を購入者向け帳票に混入させない。
- 適用範囲: 販売店業務モジュール。在庫・売買契約管理は含まない。
- 優先度: P0（代表フロー）。
- 受入条件: 第6章の仕入から納車を実行でき、整備履歴の一部だけを購入者へ公開できる。
- 根拠: 指定、資料p.9。

### FR-M03 入庫・作業承認・作業記録・引き渡しを扱う

- 利用主体: 受付・整備担当者、修理依頼者、作業承認者。
- 開始条件: 顧客が修理モジュールを有効にし、担当者が入庫・作業承認・引き渡しを進めるとき。
- 目的: 依頼内容と承認された作業範囲を取り違えない。
- 動作: 入庫時に依頼内容と状態を記録し、見積版の作業内容・金額を承認対象として提示する。追加作業は独立した承認を求め、作業記録と引き渡し記録を関連付ける。
- 例外: 拒否・期限超過の見積と追加作業は承認済みにしない。作業内容・金額を変えた場合は再提示する。承認のない範囲への着手を段階移行条件で止める。
- 適用範囲: 修理業務モジュール。MVPの見積は内容と金額の登録・添付と回答で成立させ、積算・部品発注・会計を含めない。
- 優先度: P0（代表フロー）。
- 受入条件: 第6章の入庫から引き渡しを実行でき、当初見積への承認が追加作業に流用されない。
- 根拠: 指定、資料p.9、13の修理履歴。

### FR-T01 利用環境を作り、業態テンプレートを適用する

- 利用主体: 提供側管理者・導入担当者、導入企業管理者。
- 開始条件: 提供側の導入担当者が顧客の利用環境と業態テンプレートを作成・適用するとき。
- 目的: 一店舗から複数店舗まで、共通の基盤で導入できるようにする。
- 動作: 利用環境、初期管理者、店舗、業態テンプレート、機能構成を作成し、顧客の確認後に利用開始する。テンプレートと適用した版を記録し、複数モジュールの併用も認める。
- 例外: 作成失敗時は未完了を表示し、部分的な環境を利用開始済みにしない。試行環境に別顧客の実データを流用しない。
- 適用範囲: 提供側運用、顧客管理。
- 優先度: P0。MVPの作成作業は提供側の運用手順で実施してよい。
- 受入条件: 三業態の環境を分離して作成し、適用テンプレートと機能一覧を顧客が確認できる。
- 根拠: 指定。利用開始の確認手順は追加提案。

### FR-T02 顧客別の機能・項目・業務条件を設定する

- 利用主体: 許可された導入担当者、導入企業管理者。
- 開始条件: 設定権限を持つ人が顧客の機能・項目・業務条件を変更するとき。
- 目的: コード複製に依存せず、顧客の業態・規模・運用に合わせる。
- 動作: 機能の有効化、入力・必須項目、撮影・点検、業務段階と移行条件、確認者・承認順序、通知・期限、用語、ロゴを構成する。帳票と外部接続は許可された拡張点で指定する。
- 例外: 存在しない承認者、到達不能な段階、不正な期限、機能依存の欠落を検出する。記録保全、未合意表示、企業分離、監査を設定で無効にできない。
- 適用範囲: 顧客別設定。第5章の境界に従う。
- 優先度: P0（基本構成・用語・ロゴ）、P1（複雑な分岐・独自帳票・外部接続）。
- 受入条件: 同じ共通基盤に三業態の項目と段階を設定でき、必須不足・未承認の段階移行を止める。顧客Aの変更がBへ反映されない。
- 根拠: 指定。設定の整合性検査は追加提案。

### FR-T03 設定を試行して版単位で本番反映する

- 利用主体: 導入担当者、顧客管理者、提供側保守担当者。
- 開始条件: 顧客管理者が試行済み構成の本番反映・案件移行・巻き戻しを要求したとき。
- 目的: 設定変更で進行中案件や確定記録を変えない。
- 動作: 下書き構成を試行し、差分、反映対象、互換性を確認して本番へ反映する。設定版、承認者、適用日時を残す。進行中案件への明示移行と将来案件用の巻き戻しを管理する。
- 例外: 競合する同時反映を拒否する。確定記録への遡及は拒否する。試行で署名・通知・外部送信の本番処理を誤実行しない。移行失敗時は旧版を継続し、部分適用を成功扱いにしない。
- 適用範囲: 顧客設定とテンプレート更新。具体的影響は第5章。
- 優先度: P0（試行・版管理・限定反映）、P1（多数案件の一括移行）。
- 受入条件: 撮影項目を変更しても旧案件は旧構成を表示し、移行を選んだ下書きだけが変わる。確定記録・署名・他社は不変である。
- 根拠: 指定。移行・巻き戻しの細部は追加提案。

### FR-T04 既存データを確認して取り込む

- 利用主体: 導入担当者、顧客管理者。
- 開始条件: 導入担当者が取込元・項目対応を指定し、試行または本取込を要求したとき。
- 目的: 既存の車両・担当者・履歴を導入時に利用できるようにする。
- 動作: 項目の対応付け、試行、件数・重複・エラーの確認、本取込を行う。出所、取込日時、元識別子、取込実行者を残す。既存履歴は「移行記録」として、新規の署名・検証済み記録と区別する。
- 例外: 不明な車両、他社データの混入、文字・日付不正を検出し、取込対象から外して報告する。取込の再実行で同じデータを重複作成しない。
- 適用範囲: 提供側運用。MVPは車両等の少量CSVを管理者確認付きで扱う。
- 優先度: P0（少量CSV）、P1（大量履歴・画像移行）。
- 受入条件: 正常行・重複行・不正行を含む試験データで件数と結果を照合できる。取込で提出済み記録を上書きしない。
- 根拠: 指定。CSVと移行記録の扱いは追加提案。

### FR-T05 利用状況と運用上の停滞を確認する

- 利用主体: 顧客管理者、許可された提供側担当者。
- 開始条件: 管理者が利用状況を表示し、または容量・処理件数の集計時刻になったとき。
- 目的: 容量、利用状況、未対応事項を把握して保守できるようにする。
- 動作: 利用人数、案件数、記録容量、エラー、検証待ち等を顧客単位で集計する。提供側の通常運用では業務画像や個人情報を含まない集計値を扱う。
- 例外: 集計権限から記録本文の閲覧権限を導かない。集計遅延は最終更新日時を表示する。
- 適用範囲: 提供側運用、顧客管理。
- 優先度: P0（基本件数・容量・失敗状況）、P1（詳細な分析）。
- 受入条件: 顧客が自社の容量と未完了件数を確認でき、提供側が個人情報を開かずに登録失敗の増加を把握できる。
- 根拠: 指定。集計項目は追加提案。

### FR-T06 期限と範囲を限定してサポートアクセスする

- 利用主体: 顧客管理者、提供側サポート担当者、監査担当者。
- 開始条件: 顧客がサポート許可を付与・取消しし、または許可期間が満了したとき。
- 目的: 顧客データへの恒常的なアクセスを避けつつ調査する。
- 動作: 顧客の許可、目的、対象案件・機能、操作範囲、開始・終了日時を設定して権限を付与する。実行者とサポート資格を顧客の監査履歴に残し、終了・取消しで失効する。初期は閲覧のみを標準とする。
- 例外: 自己承認、他社への権限流用、期限延長の自己操作を拒否する。記録の訂正が必要なら顧客担当者に依頼する。顧客許可なしの緊急本文アクセスはMVPに設けない。
- 適用範囲: 提供側運用。顧客内の権限管理とは別の許可として扱う。
- 優先度: P0。
- 受入条件: 許可した案件だけを期間内に閲覧でき、取消し・期限切れ後は既存セッションでも拒否する。顧客が担当者と閲覧対象を確認できる。
- 根拠: 指定。閲覧限定と緊急アクセス除外は追加提案。

### FR-T07 外部システムと許可された情報を連携する

- 利用主体: 顧客管理者、提供側連携担当者。
- 開始条件: P1として採用した接続で送受信・再送・取消しを行うとき。
- 目的: 顧客固有の既存業務へ接続できる余地を持つ。
- 動作: 連携ごとに対象項目、方向、実行権限、頻度、失敗通知、再送方針を定義する。連携資格情報は顧客単位で分離し、提供側の共通更新に追随できる拡張として管理する。
- 例外: 再送で案件・承認を重複作成しない。連携先の値で提出済み内容を上書きしない。許可を取り消した後は送受信を止める。
- 適用範囲: 追加モジュールまたは個別開発。Google Driveへの文書共有は対象外。
- 優先度: P1。MVPは出力機能で代替し、接続先を必須にしない。
- 受入条件: 採用する接続先ごとに項目・権限・再送・取消しの試験を追加し、他社の資格情報を使用しない。
- 根拠: 指定、資料p.9。接続先・形式は未決。

### FR-A01 AIで確認を支援する

- 利用主体: 記録担当者、確認者。
- 開始条件: AI機能を有効にした顧客で候補生成を実行し、人が候補を採否判定するとき。
- 目的: 傷・変化の見落としや入力負担を減らす。
- 動作: 傷・変化の候補、撮影品質の注意、入力候補を提示し、AIの提案、人の採用・修正・却下、実行日時、利用モデルを区別して残す。機能は顧客単位で選択できる。
- 例外: 未検出や誤検出を前提とし、人の確認前に確定傷・責任・請求として扱わない。障害・無効化時は手入力と目視比較で業務を継続する。画像の学習利用は別の合意なしに行わない。
- 適用範囲: 追加モジュール。責任判定・請求額決定は対象外。
- 優先度: P2。
- 受入条件: AIを無効にして第6章の三業態フローが完了する。提案を却下しても原本や人の確定結果は変わらず、提案だけで承認されない。
- 根拠: 指定、資料p.5、7〜8。資料p.14の修理費妥当性へのAI利用案は今回の対象に含めない。

## 8. 権限と共有範囲

アクセスの可否は、役割だけでなく、顧客、店舗、案件への関与、対象版、公開項目、共有期間、サポート許可を組み合わせて判定する。未許可を既定とし、画面に表示しないだけでなく、データ取得・添付取得・出力にも同じ制約を適用する。

| 主体 | 通常許可する範囲 | 制限 |
| --- | --- | --- |
| 提供側管理者・導入担当者 | 利用環境・契約構成・テンプレート・集計 | 顧客本文は別途許可が必要。導入作業にも期限と操作履歴を設ける |
| 提供側サポート担当者 | 顧客が承認した案件・操作・期間 | FR-T06の範囲外は拒否。顧客の名義で操作しない |
| 企業管理者 | 自社の構成・権限・共有方針、許可された業務情報 | 他社にはアクセス不可。提出済みの上書き不可 |
| 店舗責任者 | 担当店舗の案件・例外承認・未対応管理 | 他店舗は明示的な権限が必要 |
| 担当者 | 担当案件の作成・記録・提出・許可された共有 | 社内限定メモを外部へ公開するには別の共有権限が必要 |
| 利用者・所有者等 | 自分に提示された版、回答、許可された履歴、本人控え | 同じ車両の全案件が見られる権利にはならない |
| 外部関係者 | 指定された版・項目・期間 | 再共有・ダウンロードは個別に許可。再配布済みのファイルは技術的に回収不能 |

本人控えは、提示した記録版・確認文面とその人の回答に限定し、他の利用者の個人情報を含めない。無回答・拒否の場合も提示済み版を取得する手段を提供する。共有リンクが失効しても確認内容を振り返れるよう、本人専用の保管領域または取得済み控えを利用できる運用をMVPで用意する（追加提案）。本人確認と保管・取得の方法は導入前に定める。

通常の共有取消しは新規アクセスを停止するが、既に提示した内容を相手の回答とともに残す本人控えとは別に扱う。控えのアクセスも削除しなければならない場合は、保存・削除方針に従って理由と範囲を記録する。無期限のオンライン閲覧を約束せず、終了前に控えを取得する方法を案内する。

所有者変更は履歴への自動的な閲覧権を生じさせない。共有先への表示用コピーやマスク画像は原本と区別し、原本の検証結果と加工後表示の範囲を示す。過去の借受人の署名画像、連絡先、顔、ナンバー等に個人情報が含まれ得ることを前提に公開範囲を確認する。

## 9. 情報の関係と状態遷移

### 車両→案件→記録を軸に、版と回答を分ける

```text
顧客 → 店舗 → 案件 → 記録 → 記録版 → 原本・注釈・点検結果
車両 → 案件 ／ 関係者 → 案件での資格・期間
記録版 → 確認依頼 → 回答・署名 ／ 記録版 → 異議・訂正・補足
記録版 → 検証基準・登録状態 ／ 共有許可 → 対象版・公開項目・相手
構成版 → 案件開始時の設定 ／ 監査履歴 → 各操作の実行者・対象
```

図は概念上の関係を表し、DB設計ではない。一台の車両は複数案件を持ち、一案件は複数時点の記録を持つ。一記録は下書きと複数の提出版を持つ。関係者の個人情報は共有可能な車両履歴から分離する。テナントをまたぐ車両照合は共有の許可を代替しない。

### 記録・合意・異議・検証・業務は別々に管理する

| 管理対象 | 状態と遷移 | 変えてはいけない意味 |
| --- | --- | --- |
| 記録版 | 下書き→提出済み。提出後の訂正・補足は関連付けた新しい下書き→新しい提出版 | 提出版は固定する。「合意済み」は記録の編集可否を変える状態ではない |
| 各確認依頼 | 未回答→受領・同意・承認・拒否・保留。期限超過は未回答に付く情報 | 回答は閲覧・受領・状態同意・作業承認の種別ごとに持つ。拒否後の再回答は経緯を追記する |
| 合意の集計 | 未依頼／確認待ち／一部回答／全必要者の同意／拒否あり | 必要な全員が同じ対象版・確認事項に明示同意した場合だけ全員同意と表示する |
| 異議 | 受付→対応中→再確認待ち→解決、必要なら再開 | 全員同意後も異議は受け付ける。未解決異議があれば合意表示と併記する |
| 内部差し戻し | 要修正→対応中→再提出 | 提出版を下書きに戻さず、新しい版を作る |
| 検証基準登録 | 未登録→登録待ち→送信中→登録済み。失敗・結果未確定から照会・再試行 | 業務完了、同意、検証結果の一致を自動生成しない |
| 検証結果 | 未実施／一致／不一致／検証不能 | 登録済みでも原本未取得なら一致とはいえない。対象と実行日時を残す |
| 業務案件 | 未開始→各業務段階→完了、または中止 | 段階の順序・条件は顧客設定。完了しても異議・登録失敗は消えない |

表示例は「返却完了／提出済みv2／借受人は受領のみ・状態未同意／異議対応中／チェーン登録待ち」とする。画面の完了印一つでこれらを代替しない。再提示時は新版に対する回答を新たに求め、旧版の回答と比較できるようにする。

### チェーン内外の情報と保全範囲

| 区分 | 初期方針 | 留保 |
| --- | --- | --- |
| チェーン等の独立基準 | 記録版・原本集合のハッシュと、照合に必要な最小の参照値を登録する案 | 署名・状態をどこまで登録するかは未決。資料p.7〜8の案を固定採用しない |
| チェーン外 | 写真・動画原本、注釈、業務情報、個人情報、署名の詳細、権限、設定、検索・監査情報 | 原本・版・署名対象・ハッシュの対応を保存する。通常編集と独立基準の変更権限を分ける |
| 原本の削除後 | 残った基準値と削除経緯のみ参照可能な場合がある | ハッシュだけから写真を復元できない。基準値が残っても原本の照合はできない |

写真そのものや直接識別できる個人情報はチェーンへ載せない（資料p.8、指定）。ハッシュや参照値からの関連付け・推測の可能性も考慮し、登録内容と保存目的を採用判断時に確認する。端末の撮影日時は申告・メタデータ、サーバー受信日時はシステムが受信を記録した時刻、チェーン登録日時は登録先の処理時刻であり、いずれか一つで撮影事実の時刻を保証しない。

提出版の検証基準を生成した時点と、外部基準として保全が完了した時点を区別する。登録待ち期間の保全方式も採用判断の対象に含め、元データと同じ権限で照合値を変更できるだけの仕組みはMVPの検証受入を満たさない。

## 10. 非機能要件

分類名は指定スキルのNIST SP 800-160を参照した10分類に対応する。分類の存在と、数値・方式の合意済み判定は別である。以下の数値は実測・顧客合意のない**追加提案値**である。検証環境、端末、ネットワーク、データ量を記録し、MVPの試験前に関係者が条件を合意する。要件の有無と、提案数値への承認を区別する。

### NFR-01 認証・認可と企業間分離

- 分類: Security（認証・認可）。
- 要件: 全てのデータ参照・変更・出力・添付取得に顧客境界と権限を適用する。担当者の認証停止を反映し、管理権限・提供側アクセスには多要素認証を使う案とする。利用者確認はアカウントまたは本人向けの確認手段を選定する。
- 検証方法: 二顧客・二店舗の権限表で、直接URL、識別子差し替え、添付、検索、出力、期限切れ・停止済みセッションを試す。未許可アクセス成功0件を必須とする。本人確認方式は第13章の決定後に試験する。
- 根拠: 指定。多要素認証と本人確認案は追加提案。

### NFR-02 個人情報と公開範囲

- 分類: Privacy、Security（情報の限定と保護）。
- 要件: 収集目的、公開範囲、継続保存の目的と個別の削除条件を項目単位で整理する。期間経過による自動削除は行わない。通信と保存時の暗号化、資格情報の分離、画像内の個人情報のマスクを行う。位置情報・AI外部送信は利用目的と許可を確認する。
- 検証方法: 購入者・外部共有・本人控えを含む出力データを調べ、対象外の個人情報が0件であることを確認する。原本URLやマスク前画像の取得も試す。暗号化と秘密情報の保管設定を点検する。
- 根拠: 指定。暗号化・目的別の確認方法は追加提案。法的な保存義務の判定は未決。

### NFR-03 記録の完全性と監査

- 分類: Security、Observability（完全性と監査）。
- 要件: 提出版、署名対象、設定版の対応と追記履歴を保全する。業務データ・監査・独立検証基準の権限を分け、提供側による変更も検出可能にする。サーバー時刻を同期し、端末時刻と区別する。
- 検証方法: 原本差し替え、通常DB内のハッシュ更新、署名の別版への流用、監査の改変を試し、拒否または不一致を確認する。訂正前後・実行者・日時を再構成する。許容時刻差は運用方式を決めた後に合意する。
- 根拠: 指定、資料p.11、13。権限分離と時刻管理は追加提案。

### NFR-04 可用性

- 分類: Reliability & Resilience（可用性）。
- 要件: 提案値として月間99.5%以上のサービス可用性を目標とする。顧客が使う主要な参照・提出処理を監視し、チェーン側の停止を業務システム全体の保存失敗に波及させない。
- 検証方法: 1分間隔の外形監視を提案し、成功した観測回数／全観測回数で測る。計画停止も別記して分母に含める。観測欠損は成功扱いにしない。MVPでは障害注入と監視経路を確認し、月間実績は運用開始後に測る。
- 根拠: 指定。数値・算出方法は追加提案、契約上の保証は未決。

### NFR-05 バックアップ・復旧・事業終了への備え

- 分類: Reliability & Resilience（復旧・継続）。
- 要件: DB、原本、構成版、署名、監査、検証基準の対応を復元できること。提案値はRPO（許容するデータ損失期間）24時間以内、RTO（復旧までの時間）8時間以内とする。バックアップは別障害領域へ保管する。運営終了時は利用可能な期間内に顧客が記録と原本を出力できるようにする。
- 検証方法: 本番公開前と以後四半期ごとの復元試験を提案する。直近バックアップから別環境へ復元し、所要時間、損失範囲、署名と原本の照合、削除情報の再適用を確認する。バックアップの世代管理・復旧後の欠落通知は顧客合意で定め、業務記録の期間経過による自動削除とは分けて扱う。
- 根拠: 指定、資料p.14の運営停止への備え。数値・試験間隔は追加提案。

### NFR-06 障害・通信断で未保存を成功と表示しない

- 分類: Reliability & Resilience、Privacy（通信断・端末残存）。
- 要件: 送信前・送信中・保存済み・失敗・結果未確定を表示する。短時間の通信断で入力を失わず再送でき、重複提出・重複回答を防ぐ。端末内に一時保存する場合は対象・保存期限・消去方法を定め、他人の端末での情報残存を防ぐ。完全なオフライン業務はMVP必須としない。
- 検証方法: 撮影後、送信途中、サーバー保存後の応答前に通信を切り、再接続後の内容と件数を照合する。オフライン中の操作を相手への提示・同意・チェーン登録済みと表示しないことを確認する。
- 根拠: 指定。端末内保存方式と期間は未決。

### NFR-07 性能と画像容量

- 分類: Performance & Capacity（時間・容量）。
- 要件: 提案条件は同時利用50人、10万件の案件メタデータ、1案件20枚・1枚10MB以内の写真、実効上り10Mbps・往復遅延100msとする。この条件で通常の一覧・詳細のp95（95%の処理が収まる時間）の応答3秒以内、写真1枚の送信完了15秒以内を提案する。画像アップロードとチェーン処理は通常参照の測定から分ける。
- 検証方法: 条件を再現し、操作ごとの応答時間、エラー率、処理量、画像送信時間を測る。上限内の処理失敗率1%未満を提案する。画像超過や非対応形式は理由を返す。圧縮・プレビュー生成が原本を変更しないことも照合する。
- 測定条件案: 50人の内訳を一覧・詳細参照40人、写真送信10人とする。上り10Mbpsは送信端末ごとの実効帯域とし、共有回線の取り合いがない条件を用いる。5分間の準備後、30分間を測定し、一覧・詳細はそれぞれ1,000件以上、写真送信は100件以上の標本を得る。標本不足なら合格とせず、測定を延長する。
- 判定方法: 参照は操作開始からメタデータと一覧用画像の初回表示完了、送信は送信開始からサーバー保存完了の表示までを測る。原本の全件取得・外部登録完了は別計測とする。意図した権限拒否等を処理失敗率に混ぜず、失敗率の分子・分母とp95を操作別に報告する。条件と値はOQ-007で合意する。
- 根拠: 指定。全数値と測定構成は追加提案で、顧客の実画像・回線による再測定が必要。

### NFR-08 拡張性と容量管理

- 分類: Scalability & Elasticity（規模増加）。
- 要件: 顧客数、車両数、原本容量、検証処理の増加に対し、顧客別使用量と上限を把握できる。容量不足を事前に検知し、一社の大量処理が他社の参照・提出を継続的に妨げないようにする。動画の形式・上限はP1導入時に決める。
- 検証方法: 一社で大量出力・連続送信を行い、他社の主要操作を同時に測定する。容量80%で警告する案とし、容量超過時にも保存済みデータが失われず、新規受付の可否が明示されることを確かめる。
- 測定条件案: NFR-07のデータ量を基に二顧客を用意する。一方の顧客で写真送信10人と案件データの大量出力1件を同時実行し、他方では40人が参照する。30分の測定で他方の参照時間がNFR-07の提案値以内かを確認する。拡張検証は同時利用50人から100人へ増やして限界点を記録する案とし、100人時の保証値は未設定とする。
- 根拠: 指定。警告閾値・負荷条件・拡張範囲は追加提案。契約容量と増設判断はOQ-007で確認する。

### NFR-09 スマートフォンでの操作性

- 分類: Usability & Accessibility（操作と見やすさ）。
- 要件: スマートフォンの撮影、箇所案内、入力、比較、確認を片手操作でも進めやすくする。文字拡大、タップ領域、色だけに依存しない状態表示を備える。幅360 CSS pxで主要な操作に横スクロールを要しない案とする。
- 検証方法: iOS SafariとAndroid Chromeの導入時点の対象版を記録し、実機で三業態の撮影・共有・回答を試す。PCのChrome・Edgeも確認する。初回利用者によるタスク完了率90%以上、撮影を含む一回の受付追加操作3分以内を暫定目標として実測する。
- 測定条件案: 各業態で初回利用者10人ずつに、説明済みの一案件を初回操作してもらう。撮影8箇所の試験テンプレートを共通条件とし、実行時間は受付記録の作成開始から提出完了の表示までとする。この8箇所は測定条件であり、顧客共通の固定仕様にはしない。未完了・中断も分母に含め、支援なしの完了率と各完了例の所要時間を報告する。
- 根拠: 指定、資料p.14の3分以内という未実測目標。人数・撮影条件・幅・完了率・ブラウザーは追加提案で、OQ-007で再合意する。

### NFR-10 顧客別設定と共通基盤の保守・更新

- 分類: Maintainability & Operability（構成・更新）。
- 要件: 共通更新を顧客別のコード複製なしで適用できる。構成版の互換性、影響範囲、試行、本番反映、巻き戻し手順を持つ。過去の構成版で作成した記録を継続表示し、非対応項目を黙って削除しない。
- 検証方法: 三業態・複数構成版を使う回帰確認を行う。共通更新後に提出版の内容、署名対象、検証基準、他社設定が不変であることを照合する。移行失敗と巻き戻しも試す。
- 根拠: 指定。具体的な互換性試験は追加提案。

### NFR-11 監視とサポート

- 分類: Observability、Maintainability & Operability（監視・支援）。
- 要件: 保存エラー、認証異常、容量、バックアップ、外部登録の失敗・滞留、通知失敗を監視する。顧客の問い合わせとアクセス許可・調査履歴を関連付ける。障害時は対象範囲と暫定対応を案内する。
- 検証方法: 保存失敗と登録滞留を発生させ、提案値5分以内に担当へ通知する。通知経路停止も検出し、問い合わせからサポート操作を追跡する。受付時間・初動時間・夜間対応・費用は契約前に確認する。
- 根拠: 指定。5分と監視通知の細部は追加提案、サポート水準は未決。

### NFR-12 検証手段の継続性

- 分類: Compatibility & Interoperability（検証情報の交換）、Portability（別検証環境への移行）。
- 要件: Tapyrusの採否にかかわらず、記録版、原本、照合値、登録先参照、検証方式・版を保持する。方式変更後も過去方式の検証手順を案内し、サービス終了に備えて必要な情報を出力できる。秘密鍵を帳票や一般ログへ出さない。
- 検証方法: 出力した原本と検証情報から、提供サービスの通常DBを参照しない別の検証環境で照合し、対象版を再識別する。出力項目と方式の版、文字コード、原本への対応を文書化する。移行先の実行環境はOQ-002で方式選定時に指定し、未選定のまま長期検証可能とは判定しない。鍵の紛失・更新、登録先の停止、方式変更でどこまで検証可能かを試験・記録する。
- 根拠: 指定、資料p.11、14。鍵・ノード運用主体と長期検証方式は未決。

## 11. MVPと段階的な拡張

MVPは三業態の業務システム全体を完成させるものではなく、共通の記録基盤が三つの代表フローで成立するかを実証する。第7章のP0部分と第10章の要件を対象とし、提案数値は試験前に合意する。外部登録は画面上の疑似状態だけで済ませず、選定した検証環境で照合まで試す。

| 段階 | 対象 | 完了判断 |
| --- | --- | --- |
| MVP | P0の共通基盤、三業態の最小フロー、項目・段階・承認・期限の基本設定、標準帳票、少量取込、サポート許可 | 第12章の受入条件を満たし、未決の導入条件を合意できる |
| 導入拡張 | P1の動画、大量移行、高度な承認・通知、独自帳票、外部連携 | 顧客ヒアリングで必要性と運用負担を確認し、個別の受入条件を追加する |
| 将来検証 | P2のAI支援、他サービスとの連携拡大、車両以外への適用 | 人の判断と共通基盤の保全条件を維持できることを検証する |

### 中核実証と実データ導入の確認を分ける

最も大きな仮説は「業態ごとにコードを複製せず、同じ記録・共有・確認・検証基盤で三つの代表フローを扱える」である。まず架空データの限定環境でGOAL-001〜GOAL-004を測る。実データを使う前には、本人確認、保存・削除、復旧、サポート許可等のP0条件も確認する。中核デモの成功だけで本番利用可能と判断しない。

| 確認段階 | 最小の成立条件 | 範囲を広げないための扱い |
| --- | --- | --- |
| 中核実証 | 三業態の一連の記録・提示・回答・比較・検証、未署名と設定分離のケース | 架空案件を使用。予約・決済・会計・在庫を必須にしない |
| MVPの実データ導入前 | 第7章のP0部分、第10章の合意した条件、Open事項のうち導入前ゲートの解決 | データ量・顧客数・期間を限定し、未達時は拡大を止める |
| 導入拡張 | P1・P2を採用するときの個別条件 | 将来機能の未実装をMVPの不合格と混同しない |

管理者向けの見た目を整えた設定エディター、独自帳票レイアウト、大量処理の自動化はP0の成立条件にしない。FR-T01、FR-T03、FR-T04、FR-T05は、権限を持つ提供側担当者の確認付き手順でもよいが、構成差分・実行結果・監査証跡は必要である。FR-C17の削除も初期は承認付き手順を認める。基本通知は一つの経路、帳票は標準形式とし、ロゴ設定は既存の枠への適用に留める。これらは要件を省くのではなく、MVPで提供する方法の境界を定める。

P0の実装量・運用量が体制に収まるかはOQ-010で評価する。MVPの範囲変更が必要なら、削る項目、失う受入価値、代替手段を依頼者へ提示し、要件版を更新する。

MVPでの提供側作業は、管理画面の完成に限らず、権限・版・実行履歴を持つ運用手順で実施してよい。ただし顧客が設定差分を確認でき、他社分離、サポート許可、確定記録保全を実際に試験できることを条件とする。AIや外部業務システムがなくても基本業務を実行する。

## 12. 受入条件と確認する証跡

本章は今後の製品受入の条件であり、今回の文書作成で製品試験が完了したことを示さない。架空データを使い、環境・構成版・記録版・実施者・日時・結果・画面または出力を証跡として残す。

ACのIDは受入のまとまりを表す。表の各行は「前提（Given）→操作（When）→期待結果（Then）」の一ケースで、独立に合否を判定する。1ケースの成功で同じACの他ケースも合格と扱わない。MVPはP0のケースを必須とし、P1・P2のケースは採用時に検証する。FRの本文にある例外と受入条件も確認対象であり、対応表の参照があるだけでは受入完了にならない。

- 操作: 各ケースの担当者が、対象業務の開始から引き渡しまでを操作する。
- 期待結果: それぞれのケースが、専用のコード複製や対象外機能を要さずに完了する。

| ケース・前提 | 操作 | 期待結果 |
| --- | --- | --- |
| 1: レンタカーの貸出案件 | 貸出前記録→提示→貸出→返却比較を行う | 同じ案件に貸出・返却の記録版が関連付く |

### AC-09 訂正と作業承認の対象を維持する

- 条件: 署名済み記録と承認済み見積を用意する。

案件の主対象車両は一台、初期言語は日本語、主な記録端末はスマートフォンのブラウザーとする。MVPは一つの共通基盤に顧客別の論理的な利用環境を持つ案とし、専用環境の必要性は顧客ごとに確認する。顧客は担当者と利用者へ記録・共有・保存の目的を説明する主体、提供側は契約に基づく運用主体と仮定する。法的な役割分担は別途確認する。
