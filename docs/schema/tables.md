## 方針

### スキーマを三つに分ける

| スキーマ | 内容 | 主な要件 |
| --- | --- | --- |
| `app` | 組織、構成版、車両、案件、記録、確認、異議、共有などの業務データ | FR-C01〜C18、FR-T01〜T06 |
| `integrity` | 検証基準（ハッシュの束と外部登録の状態）と照合結果 | FR-C09、FR-C10、NFR-03、NFR-12 |
| `audit` | 操作とアクセスの履歴 | FR-C16 |

`integrity` と `audit` を分けるのは、アプリが使う DB ロールの権限を変えるためです（後述の「DB ロールと権限」）。

### 顧客（テナント）の分離

- 顧客のデータを持つテーブルには、すべて `tenant_id` を持たせます。
- 参照は `(tenant_id, x_id) REFERENCES t (tenant_id, id)` の複合外部キーにします。A 社の案件から B 社の店舗や車両を指す行は DB が拒否します（NFR-01）。
- 案件の下にある表どうしの参照は、さらに `case_id` も含めます。別の案件の写真や記録版を指す行も作れません。
- 例外は、顧客をまたぐ `tenants`、`provider_operators`、`business_templates` への参照と、事業者間の共有（`share_grants.recipient_tenant_id`）だけです。
- 複合外部キーで止められるのは、顧客をまたぐ参照だけです。読み書きのときに他社の行に触れないようにするのは、アプリの検索条件か行レベルセキュリティ（RLS）です。RLS を重ねて使うかは、実装時に決めます。

## 書き方の決まり

テーブルごとに書き方がばらつかないよう、次の決まりで揃えました。マイグレーションで表を足すときもこれに合わせます。

### 作った人と日時

- 業務の行は `created_by`（担当者）と `created_at` を持ちます。
- 作る人が担当者・関係者・提供側のどれか決まらない表は、`created_by_staff`、`created_by_participant`、`created_by_operator` のうち必要な列を置き、どれか一つだけ入るよう CHECK で縛ります（`num_nonnulls(...) = 1`）。
- 顧客や店舗、車両などの基本の表と、システムが作る行（通知、本人控え、検証基準など）は作った人の列を持ちません。だれが操作したかは `audit.events` に残します。
- 回答（`confirmation_responses`）の回答者は依頼の相手なので持ちません。担当者が代わりに入力したときだけ `proxy_by` を入れます。

### 一度きりの出来事と状態

- 提出、反映、取消しのように一度しか起きない出来事は、`<動詞>_by` と `<動詞>_at` の組で持ちます。システムの出来事は `_at` だけです。組の片方だけが入った行は CHECK で止めます。
- 三つ以上の状態を持つものは `status` 列（`text` と CHECK）にします。enum 型は値の削除や並べ替えが難しいので使いません。
- 状態のある行は最初の状態でしか作れません（構成版は `draft`、取込は `trial`、検証基準は `unregistered`）。途中の状態の行をいきなり作ると、その前の段階の確認を飛ばせてしまうためです。共有も発行前の状態でしか作れません。
- 状態を行き来した経緯は列にせず、`audit.events` に残します。
- 端末が申告した時刻は `device_` を付けて、サーバーの時刻と区別します（`device_captured_at`、`device_sent_at`）。

### 書き換えと削除

- どの表も、更新してよい列をトリガー（`app.allow_columns`）で決めています。書いていない列を変えると止まります。
- 終わった行（提出済み、反映済み、取消し済み、解決済みなど）は、それ以上変えられません。
- やり直しは行を書き換えず、新しい行を足します（訂正版、答え直し、判定のやり直し、通知の再送など）。
- 業務の記録は行を消しません。写真の原本と本人控えはファイルを消しても行を残し、`deleted_at` を入れます。個人情報は `parties.erased_at` を入れて中身だけ消します。
- 行のトリガーは TRUNCATE では動かないので、すべての表に TRUNCATE を止めるトリガーも付けています。

### 参照と値の形

- `_id` で終わる列は、すべて本当の外部キーです。構成版の中の項目名のように外部キーにできない識別子は `_key` で終わらせます（`item_key`、`spot_key`、`statement_key`）。
- 配列の列は使いません。一対多は子の表にします。
- `jsonb` は、形が顧客や外部サービスごとに変わるものだけに使います（`definition`、`settings`、`payload`、`value`、`vehicle_snapshot`、`details`、`response`）。

### 同じ事実を二か所に持つところ

原則として一つの事実は一か所にだけ持ちます。次は理由があって重ねて持っています。

| 列 | 理由 |
| --- | --- |
| 子の表の `tenant_id`、`case_id` | 複合外部キーで顧客や案件をまたぐ参照を止めるため |
| `record_versions.vehicle_snapshot` | 提出したときの車両の表示を残すため。あとでナンバーが変わったり車両を統合したりしても、提出版の表示は変えない |
| `record_versions.configuration_version_id` | 案件は新しい構成版へ移ることがあるので、版ごとに入力に使った構成版を残す |
| `confirmation_responses.confirmation_type` | 依頼の種類の写し。依頼と複合外部キーで一致させたうえで、種類ごとに選べる答えを CHECK で絞る。この列を消すと、同じ確認をトリガーで書くことになる |
| `objection_items.record_version_id` | 異議の版の写し。異議と項目の両方に複合外部キーを張り、異議を出した版の項目しか指せないようにする |
| `content_hash`、`manifest_hash` | 中身から計算できる値だが、提出時点の値を照合の基準として残す |

`record_entries` は項目を列ではなく1項目1行で持ちます。項目は顧客ごとの構成版で決まり、テーブルの列にできないためです。値の型は構成版の項目定義で確かめます。

## 再送で重複させない

通信が切れたあとに同じ操作が再送されても二重に登録しないよう、端末やワーカーが作るキーに一意制約を付けます（NFR-06）。

| 操作 | キー |
| --- | --- |
| 写真のアップロード | `media_originals.idempotency_key` |
| 記録版の提出 | `record_versions.submit_idempotency_key` |
| 確認への回答 | `confirmation_responses.idempotency_key` |
| 外部登録の送信 | `integrity.anchor_transactions.txid`（送る前に保存した署名済みのトランザクションを、再送でもそのまま送る） |

外部登録の試行（`anchor_attempts`）にはキーを持たせず、`anchor_id` と `attempt_no` の組で一回ごとの試行を見分けます。

Tapyrus に送る署名済みのトランザクションは、送る前に `anchor_transactions` に保存します。送った後に応答が返らないまま落ちても、保存した txid で照会でき、見つからなければ同じバイト列を再送できます。試行は、どのトランザクションを送ったか、照会したかを `transaction_id` で必ず指します。トランザクションを作り直したときは行を足し、前の行も残します。

下書きの同時編集は `record_versions.lock_version` で検出します（楽観ロック）。提出する処理（Go 側）は、記録版の行を `SELECT ... FOR UPDATE` で押さえてから、状態と `lock_version` を確かめ、子の表（項目、写真、傷、撮影不能の理由）を読んで検証し、ハッシュを計算して提出済みにします。この順にすると、検証してから提出するまでの間に子の表を書き換えられません。

## 個人情報を分ける

氏名、電話番号、メールアドレス、住所は `parties` だけに持ちます。案件や記録からは `party_id` や関係者の行で指すだけにして、共有や削除の範囲を決めやすくしています（NFR-02、FR-C17）。

ただし、写真、自由記述の欄、署名、本人控えにも個人情報が写ったり書かれたりすることがあります。削除の対象は `parties` だけでなく、これらも含めて管理します。

## 保存しないもの

次はほかの表から求められるので、列にしていません。

- 仮登録の車両: 確認済みの車台番号か VIN がない車両です。
- 合意状態（未依頼、一部合意など）: 確認依頼と、それぞれの最新の回答から集計します。無回答と期限切れは回答の行がないことと `due_at` で分かります。
- 異議や差し戻しで訂正した箇所: 元の版と訂正版の項目を比べれば分かります。
- 取込の件数: `import_job_rows` から数えます。
- 外部登録が止まっているか: `anchor_attempts` の時刻と結果から判断します。
- 検証の「未実施」: `verification_runs` に行がないことで表します。
- 利用状況（FR-T05）: 件数と容量は集計クエリで出します。足りなければ集計の表を足します。

### 組織と権限

| テーブル | 内容 | 要件 |
| --- | --- | --- |
| `tenants` | 顧客。provisioning / active / suspended / closed | FR-C01、FR-T01 |
| `stores` | 店舗 | FR-C01 |
| `staff_members` | 顧客側の担当者。退職しても行は残す | FR-C01 |
| `provider_operators` | 提供側の担当者。顧客をまたぐ | FR-T06 |

最後の管理者を外せないようにする制御は、行をまたぐ条件なのでアプリ側で行います。

### 記録と写真

| テーブル | 内容 | 要件 |
| --- | --- | --- |
| `records` | 案件の中の記録（貸出前点検、見積など） | FR-C04 |
| `record_versions` | 記録の版。下書きは一つの記録に一つ。訂正と補足は元の版を指す新しい版にする | FR-C04、FR-C07、FR-C11 |
| `record_entries` | 点検結果や見積の金額などの入力値。1項目1行 | FR-C04、FR-C08 |
| `media_originals` | 写真の原本。SHA-256、端末の撮影日時、任意の位置 | FR-C04、NFR-07 |
| `media_annotations` | 原本に付けた注釈、マスク、切り抜き。加工した画像は別のファイルにする | FR-C04、FR-C12 |
| `record_version_media` | 記録版に含める写真と撮影箇所 | FR-C04、FR-C05 |
| `damage_marks` | 傷の位置と説明 | FR-C04 |
| `capture_exceptions` | 撮影できなかった箇所の理由と、認めた責任者 | FR-C05 |
| `record_comparisons` | 二つの提出版の同じ箇所を比べた判定と根拠 | FR-C06 |

写真の原本は案件に属します。訂正版でも同じ写真をそのまま指せるようにするためです。見積の内容と金額は記録版の項目として持つので、確認依頼の側には持ちません。

比較の判定を直すときは、`revision_no` を一つ増やした行を足します。いまの判定は `revision_no` がいちばん大きい行です。同じ処理の中で足した行は `created_at` が同じになるので、日時では順番を決めません。

### 異議と差し戻し

| テーブル | 内容 | 要件 |
| --- | --- | --- |
| `objections` | 関係者からの異議と社内の差し戻し。受付の可否、担当、対応の結果 | FR-C13 |
| `objection_items` | 異議の対象の項目。異議を出した版の項目に限る | FR-C13 |
| `objection_evidence` | 異議に添えた写真 | FR-C13 |

異議と差し戻しは、出した人が関係者か担当者かの違いだけなので一つの表にしました。社内の差し戻しには受付期限がないので、受付の可否は入れられません。

### 確認

| テーブル | 内容 | 要件 |
| --- | --- | --- |
| `confirmation_requests` | 確認の依頼。対象の版、相手、種類（閲覧、受領、状態合意、作業承認）、見せた文面、文面の元とその版、期限 | FR-C08 |
| `confirmation_responses` | 回答。答え直しも行を足す。代理の根拠、本人確認の方式 | FR-C08 |
| `request_notifications` | 依頼の通知を送った記録。届いた・開いたことは回答として扱わない | FR-C14 |
| `personal_copies` | 本人控え。依頼した版と本人の回答をまとめたファイル | FR-C15 |

受領の依頼に「同意」で答えるような、種類と合わない回答は CHECK で止めます。

`statement_text` には、相手に見せた文面を、差し込む項目（ナンバーなど）を埋めた状態でそのまま入れます。`statement_key` と `statement_version` は文面の元がどれかを表すだけなので、あとで元の文面を直しても、当時何を見せたかは `statement_text` で分かります。依頼を作った後は変えられません。

### 共有

| テーブル | 内容 | 要件 |
| --- | --- | --- |
| `share_grants` | 共有の許可。相手は社外の人か別の事業者。目的、ダウンロード可否、期限、発行、受け入れ、取消し | FR-C12、FR-C18 |
| `share_grant_targets` | 共有する記録版 | FR-C12 |
| `share_grant_items` | 共有する版のうち相手に見せる項目 | FR-C12 |
| `share_grant_media` | 共有する写真と、掛けるマスク | FR-C12 |

共有は発行前の状態で作り、範囲（対象の版、項目、写真）を決めてから発行します。相手に見せるのは発行した後で、発行した後は範囲を足せません。範囲を変えるときは共有を取り消して作り直します。共有リンクのトークンはハッシュだけを持ちます。

発行するときは、発行日時が期限より前か（CHECK）と、DB の時刻で期限が切れていないか（トリガー）を確かめます。`issued_at` は呼び出し側が入れる値なので、CHECK だけだと日時をさかのぼって入れれば期限切れでも発行できてしまうためです。受け入れるときやリンクを開いたときに期限が切れていないかは、Go 側で確かめます。

マスクに指定できるのは、消していない `kind = 'mask'` の注釈だけです。

### 継続保存と個別の削除

記録・写真原本・本人控え・共有情報・監査履歴は、期間経過による自動削除を行いません。共有の `expires_at` はアクセス許可の期限であり、記録を削除する期限ではありません。圧縮・アーカイブは別途検討します。

| テーブル | 内容 | 要件 |
| --- | --- | --- |
| `deletion_requests` | 削除の申請、保留、承認、実行。対象は案件か社外の人 | FR-C17 |

`000002` で `retention_policies` を廃止します。既存の設定値（NULL を含む）は、削除前に `audit.events` へ顧客ごと・対象ごとに追記します。`action = 'retire_retention_policy'`、`details.policy` に旧設定の全列、`details.migration` に移行名を残します。これは過去の設定の記録で、保存期限の設定としては使いません。監査行の `entry_hash` は、Migration 内で組み立てたイベントの JSONB テキストを UTF-8 にして SHA-256 を計算します。

退避とテーブル廃止は一つのトランザクションで行い、設定テーブルをロックして同時更新を防ぎます。業務記録、原本の参照情報、検証基準、既存の監査履歴、個別の削除申請は変更しません。必要な個別の削除は、理由と承認・実行の経緯を残して扱います。

### 検証

| テーブル | 内容 | 要件 |
| --- | --- | --- |
| `integrity.anchors` | 提出版の検証基準。登録した内容（manifest）とそのハッシュ、方式、登録の状態 | FR-C09、FR-C10 |
| `integrity.anchor_transactions` | 送る前に保存する署名済みのトランザクションと txid。変えない | FR-C10 |
| `integrity.anchor_attempts` | 登録と照会の試行。送る前に行を作り、再送の前に照会する。試行ごとに `attempt_no` を 1 から振る。送ったか照会したトランザクションを指す | FR-C10 |
| `integrity.verification_runs` | 照合の結果。一致、不一致、照合不能 | FR-C09 |

照合は `registered` の検証基準だけを信じるので、成功した試行（`outcome = 'succeeded'`）がない基準は `registered` にできません。`external_ref` も、成功した試行が指すトランザクションの txid と一致しなければなりません。登録の送信が時間切れになり、照会で登録が見つかった場合も成功に数えます。

検証基準は「記録版と方式」の組で一つです。方式を変えるときは新しい行を足し、古い基準も残します（NFR-12）。

### 監査

| テーブル | 内容 | 要件 |
| --- | --- | --- |
| `audit.events` | 操作とアクセスの履歴。だれが、どの資格で、何に、何をして、結果がどうだったか | FR-C16 |

業務の行が消えても履歴は残すため、この表だけは外部キーを張りません。パスワードやトークンは `details` に入れません。

### テーブルにしていないもの

- FR-T05（利用状況）: 集計クエリで出します。
- FR-T07（外部連携）と大量の移行: P1 なので、接続先が決まってから設計します。移行した記録の目印も、そのときに足します。
- 認証情報: 本人確認の方式（OQ-001）が決まってから足します。

## DB ロールと権限

アプリのロールが何でもできると、DB を直接書き換えられたときに検証の意味がなくなるので、ロールを分ける案です。DDL にはまだ入れていません。

| ロール | 権限 |
| --- | --- |
| マイグレーション用 | スキーマの変更。アプリの実行時には使わない |
| アプリ用 | `app` の読み書き。`audit` と `integrity.verification_runs` は INSERT と SELECT だけ。TRUNCATE はどの表にも渡さない |
| 登録処理用 | `integrity.anchors`、`integrity.anchor_transactions`、`integrity.anchor_attempts` の読み書き。外部登録のワーカーだけが使う |
| 閲覧用 | 監査や調査のための SELECT だけ |

PostgreSQL 14 では、だれでも `public` スキーマに表や関数を作れます。ロールを作るときに `REVOKE CREATE ON SCHEMA public FROM PUBLIC` も入れます。

DB の中で守るだけでは、提供者から独立した検証にはなりません。DB の管理者はトリガーも外せるからです。提出後の改変を第三者が確かめられるようにするには、ハッシュの外部登録（FR-C10、OQ-002）が要ります。

## マイグレーション

- ツールは [golang-migrate](https://github.com/golang-migrate/migrate) を使います。SQL ファイルをそのまま流せて、関数やトリガーにも特別な書き方が要らないためです。Atlas は関数とトリガーの管理が有料版の機能なので外しました。
- GORM の AutoMigrate は使いません。トリガー、部分一意インデックス、CHECK 制約、権限を表せないためです。
- ファイルは `backend/db/migrations/` に、`000001_init.up.sql` のような連番の名前で置きます。
- 1 ファイルは一つのトランザクションで流れます。golang-migrate はファイル全体を一度に送り、PostgreSQL はそれを一つのトランザクションとして扱うので、途中で失敗しても何も残りません。ただし golang-migrate はその版を dirty として記録するので、ファイルを直したら `migrate force` で記録を戻してから流し直します。
- golang-migrate の `x-multi-statement` は有効にしません。`;` で文を切って一つずつ流すので、関数の本体が途中で切れ、一つのトランザクションにもならないためです。
- `CREATE INDEX CONCURRENTLY` のようにトランザクションの中で動かない文は、その文だけのファイルに分けます。
- down のファイルは作りません。直すときは新しい番号のファイルを足します。開発中に作り直したいときは、DB ごと消して流し直します。
- 共有の DB に流した後のファイルは直しません。それまでは `000001_init.up.sql` を直接直してかまいません。
- 本番では戻さずに進めます。列の削除や型の変更は、新しい列を足す、両方に書く、読み先を移す、古い列を消す、の順に分けます。
- 提出済みのデータはマイグレーションでも書き換えません。ハッシュの計算方法を変えるときは `hash_algorithm` や `method_version` を変えて、新旧を区別します。
- 表を足すときは、更新を制限するトリガーと TRUNCATE を止めるトリガーも付けます。付け忘れは `rules.sql` で見つかります。
- 業態テンプレートなどの初期データは、スキーマのマイグレーションとは分けて入れます。
- アプリの起動時に流すか、CLI で流すかは、DB への接続を作るときに決めます。

### 確かめ方

[`backend/db/test/run.sh`](../../backend/db/test/run.sh) は、空の DB を作ってマイグレーションを番号順に流し、制約のテスト（`constraints.sql`）、書き方の決まりの確認（`rules.sql`）、同時実行のテスト（`concurrency.sh`）をします。終わったら DB を消します。PostgreSQL 14 以上と psql が要ります。接続先は `PGHOST` などの環境変数で指定し、DB を作れるロールで実行します。

同じスクリプトから別の一時 DB で `test/upgrade.sql` も実行します。初期版に記録・原本の参照情報・検証基準・保存日数設定を入れて `000002` を適用し、旧設定の退避と業務データの保持を確認します。

止まるはずの操作は `pg_temp.ng(ラベル, SQL, SQLSTATE, 制約名)` で書きます。制約で止まるもの（23503 外部キー、23505 一意、23514 CHECK など）は、SQLSTATE と制約の名前を書きます。トリガーで止まるものはどれも SQLSTATE が P0001 になるので、`expected_message =>` でトリガーのエラー文も書きます。比べるのは 000001 のトリガーに書いたエラー文だけで、PostgreSQL 自身のエラー文は比べません。参照先の行がない、列名を間違えたなど、違う理由で止まったときも NG になります。`ng()` の中で作った行は取り消されるので、後のテストの準備には使えません。

通るはずの操作は `pg_temp.ok(ラベル, SQL)` で書きます。UPDATE は対象が 0 件でも成功するので、保存された値まで見たいところは `pg_temp.assert_true(ラベル, 条件)` で確かめます。これらの関数は `helpers.sql` にあります。

テストは最初の NG で止まり、`run.sh` は失敗で終わります。`rules.sql` も、決まりから外れた表や列を全部 NG の行で出してから失敗します。

同時に二つの接続から操作したときの動きは `concurrency.sh` で確かめます。先の接続は BEGIN して文を流し、後の接続がそのロックを待ち始めたことを `pg_blocking_pids()` で見てから COMMIT します。後の接続は、先の接続が確定した後に想定した理由で止まることを `ng()` で確かめます。後の接続が待たずに進んだときも NG になります。`constraints.sql` で作った行を使うので、その後に流します。

```bash
PGHOST=localhost PGUSER=postgres backend/db/test/run.sh
```

手元に PostgreSQL がなければ、compose の `db` に対して流せます（`bash scripts/init.sh` の後）。CI でも同じものを流します。

```bash
docker compose run --rm db-test
```

## 確認したこと

初期版は WSL の PostgreSQL 14.18 と compose の PostgreSQL 17.11 で、46 表と 269 件の操作・確認を検証しました。`000002` を含む現行版は専用の PostgreSQL 17 コンテナで `run.sh` を実行し、制約・同時実行・既存 DB の移行を合わせて 317 件の確認が成功しました。移行試験では、旧設定を監査履歴へ退避し、業務データが移行前後で同じであることを確かめています。主な制約の確認内容は次のとおりです。

- 他の顧客の店舗や車両を指して案件を作る、別の案件の写真を記録版に入れる
- 下書きの構成版で案件を作る、案件と違う構成版で記録版を作る、移した案件を置き換わった構成版へ戻す、移した案件の下書きを旧版のまま提出する
- 本番の構成版を二つにする、反映済みの構成版や業態の組み合わせを変える、構成版や取込や検証基準を途中の状態でいきなり作る
- 同じ役割を全店舗で二重に付ける、同じ店舗で二重に付ける（別の店舗には付けられる）
- 記録に下書きを二つ作る、提出版とその項目・写真・傷を変える・消す
- 原本のハッシュを変える、原本の行を消す
- 比較の判定を同じ `revision_no` で二つ作る（いまの判定が `revision_no` のいちばん大きい行で選べることも確かめる）
- 下書きに確認依頼や異議を出す、見せた文面が空の依頼を作る、見せた文面を書き換える、受領の依頼に同意で答える、同じ回答を再送する
- 共有する版に含まない写真を共有する、別の写真のマスクやマスクでない注釈を掛ける、発行した共有に範囲を足す、発行済みや取り消し済みの状態で共有を作る、発行前に受け入れる、期限より後の日時で発行する、期限が切れた共有を日時をさかのぼって発行する
- 外部登録の試行の番号を二度使う（同じ登録の再試行は番号を変えて足せる）、成功した試行がないまま、または成功した試行と違う txid で検証基準を登録済みにする
- 同じ txid のトランザクションを二つ保存する、形の違う txid を保存する、保存したトランザクションを書き換える・消す、トランザクションを指さずに送信や照会の試行を作る、別の検証基準のトランザクションを送る
- 統合が輪になる車両の統合、同じファイルの二度目の本取込
- 検証基準のハッシュを変える、理由なしで照合不能にする、未登録の基準で一致にする、監査履歴を書き換える・TRUNCATE する
- 二つの接続から同時に、提出と項目の追加、共有の発行と範囲の追加、同じ顧客の構成版二つの反映、二台の車両の互いの統合、同じ記録への下書き二つを行う（後の接続が待たされ、先の接続が確定した後に止まり、片方だけが残る）

あわせて、書き方の決まりを守れているかをカタログから引くクエリで確かめました（外部キーのない `_id` 列、`_by` と `_at` の組、配列の列、`tenant_id` や `case_id` を含まない外部キー、更新の制限がない表、TRUNCATE を止めていない表など）。更新の制限と TRUNCATE の確認では、トリガーが有効で、BEFORE で動き、条件や列の指定なしにすべての更新で動くか（TRUNCATE は `app.reject_change()` を呼ぶか）まで見ます。

テストの側が正しく失敗するかも、わざと壊した写しで確かめました（SQLSTATE、制約の名前、トリガーのエラー文をそれぞれ変える、P0001 なのにエラー文を書かない、存在しない列名を書く、`assert_true` の条件を変える、決まりに反する表を足す、トリガーを無効にする、`ok()` の中身を失敗させる、車両の統合や子の表のトリガーでロックを取らないようにする、試行のトランザクションを必須にしない、登録済みにするときに txid を比べない、同じ検証基準のトランザクションだけを指す外部キーを外す、保存したトランザクションの UPDATE を止めない）。どれも `run.sh` が失敗で終わります。
