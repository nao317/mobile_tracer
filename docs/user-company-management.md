# ユーザー・企業・申請の管理

一般ユーザーから業者ユーザーへの変更、企業とプロファイルの作成、所属企業のプロファイル変更は申請制とする。申請の保存だけでは区分・企業・プロファイルを変更しない。システム管理者が承認した時点で反映し、拒否した場合は理由を申請者に表示する。

## 画面と権限

| 画面 | パス | 利用者・操作 |
| --- | --- | --- |
| システム管理の概要 | `/admin` | システム管理者。ユーザー数・企業数・承認待ち件数を確認 |
| ユーザー管理 | `/admin/users` | システム管理者。検索、表示名・一般／業者区分・利用状態の変更、所属企業の確認 |
| 企業・プロファイル管理 | `/admin/companies` | システム管理者。企業の作成・検索・情報と状態の更新、業者ユーザーの所属追加・解除 |
| 申請の一元管理 | `/admin/requests` | システム管理者。全申請の検索、種別・状態での絞り込み、理由を付けた承認・拒否、履歴の確認 |
| 自分の申請・企業 | `/account/requests` | 一般ユーザーは業者変更申請。業者ユーザーは企業・プロファイル作成申請と所属企業のプロファイル変更申請。自分の履歴・審査結果の確認 |

アカウント画面から各画面へ移動する。管理者はFirebaseで確認済みのメールと`SYSTEM_ADMIN_EMAILS`を照合して判定する。指定するアカウントは`nao.yellowtail.1729@gmail.com`。メール文字列や区分をブラウザーから送って管理者権限を得ることはできない。システム管理者の権限と、企業内の業務権限は別に扱う。

設定の入口は`/settings`。アカウント、表示設定、自分の申請、所属企業へ移動する。所属を選択していない利用者も、セッション認証で設定と申請を利用できる。

一覧は検索と結果に絞り、作成・編集・審査は次のURLで開く。queryも画面の状態として扱うため、直接アクセスと再読み込みで同じ操作を開ける。

| 入口 | 作業別URL |
| --- | --- |
| `/admin/users` | `?user=:id&view=detail`、`?user=:id&view=edit` |
| `/admin/companies` | `?company=:id&view=detail`、`?company=:id&view=edit`、`?company=:id&view=members`、`?view=new` |
| `/admin/requests` | `?request=:id&view=detail`、`?request=:id&view=review` |
| `/account/requests` | `?view=history`、`?view=detail&request=:id`、`?view=upgrade`、`?view=new-company`、`?view=companies`、`?view=company&company=:id`、`?view=profile&company=:id` |

自分の承認待ち申請は、履歴の表示ページとは別の問い合わせで確認する。所属追加・初期管理者の候補検索は、企業作成または所属管理の画面で取得する。

候補検索は20件ずつAPIから取得し、所属者は詳細レスポンスの全配列を20件ずつ表示する。検索条件とページは一覧から詳細・編集へ引き継ぐ。戻り先は同じ管理画面内のパスとして検証する。

申請APIには単件取得がないため、申請詳細・審査は一覧APIを100件ずつ取得して対象IDを探す。履歴の検索条件や審査による状態変更にかかわらず開けるが、対象までの取得回数は履歴件数に依存する。UI分割のために新しいAPIは追加していない。

一般ユーザーは自分の区分を直接変更できない。業者ユーザーも企業情報を直接反映できず、申請には管理者の承認が必要。自分が所属しない企業への変更申請は拒否する。システム管理者は管理画面から直接変更でき、その操作も監査履歴へ記録する。

## 企業と所属

企業プロファイルは正式名称、紹介文、Webサイト、電話番号、住所、連絡先メール、業態を持つ。業態はレンタカー・カーシェア、販売店、整備・修理から1つ以上選ぶ。

企業の作成を承認すると、企業・プロファイル・本店・最初の企業管理者の所属・初期の業務構成を一つのトランザクションで作る。申請者が最初の企業管理者となる。管理者が直接作成する場合は、有効な業者ユーザーを企業管理者として指定する。作成後はアカウント画面で所属を選択すると業務画面を利用できる。

初期の業務構成は受付と点検、走行距離・メモの基本項目を持つ。プロファイルの業態変更は企業の紹介情報を更新するもので、公開済みの業務構成や既存案件の構成版を変更しない。

所属追加はユーザーIDを明示して行い、メールアドレスの一致だけでは紐付けない。所属を再追加する場合は、過去の明示的な紐付けと同じ担当者・役割を使う。既存の複数役割・店舗単位の役割編集は、この画面の対象外。最後の有効な企業管理者の所属解除は拒否する。システム管理者による利用停止・一般区分への変更は実行できるため、必要に応じて先に別の企業管理者を追加する。

一般ユーザーへ戻すと有効な所属と選択中の所属を解除する。利用停止では既存セッションを失効させる。利用再開後は再ログインが必要で、解除した所属も自動復元しない。自分自身のシステム管理者アカウントは停止できない。企業を停止するとその企業の業務APIへのアクセスを拒否する。

## 審査と競合

- 同じ申請キーによる再送は同じ申請を返す。同じキーで内容を差し替えることはできない。
- 同じ利用者・種別・対象企業について、承認待ちの申請は1件とする。
- 審査は行をロックして実行する。同じ承認を再送しても企業・所属・監査履歴を重複作成しない。審査済みの申請を反対の結果へ変更することはできない。
- 承認・拒否とも理由が必須。申請内容、審査者、日時、理由を保持し、審査済みの申請は更新・削除しない。
- 企業・ユーザーの直接編集とプロファイル変更申請には版番号を使う。提出後に企業情報が更新されていた場合は承認を拒否し、申請を承認待ちのまま残す。最新版を確認して拒否・再申請する。
- 監査保存を含めて処理を確定する。監査保存に失敗した場合は、承認結果と権限・企業情報の変更もロールバックする。

画面は送信中の再操作を防ぎ、未保存の入力を残して移動するときは確認を表示する。通信失敗などで結果が未確定の場合は、一覧で結果を確認してから再操作する。

## API

各APIはFirebaseセッションを毎回検証する。`/api/admin/*`はシステム管理者に限定する。更新には同一オリジンとCSRFトークンが必要。

| 方法 | パス | 内容 |
| --- | --- | --- |
| GET | `/api/me/requests` | 自分の申請のみを取得 |
| POST | `/api/me/requests` | `request_key`、`kind`、`payload`、変更申請では`company_id`を指定 |
| GET | `/api/me/companies` | 自分の有効な所属から企業・プロファイルを取得 |
| GET | `/api/admin/overview` | 管理件数 |
| GET | `/api/admin/users`、`/api/admin/users/:id` | ユーザー一覧・詳細と所属企業 |
| PATCH | `/api/admin/users/:id` | 表示名・区分・状態・版番号を指定して更新 |
| GET | `/api/admin/companies`、`/api/admin/companies/:id` | 企業一覧・詳細と所属者 |
| POST | `/api/admin/companies` | 企業・プロファイル・初期管理者を指定して作成 |
| PATCH | `/api/admin/companies/:id` | 企業名・プロファイル・状態・版番号を指定して更新 |
| POST | `/api/admin/companies/:id/members` | 業者ユーザーを役割付きで所属させる |
| POST | `/api/admin/companies/:id/members/:linkID/revoke` | 理由付きで所属解除 |
| GET | `/api/admin/requests` | 全申請。`kind`・`status`・申請者メールで絞り込み |
| POST | `/api/admin/requests/:id/decision` | `decision`に`approved`または`rejected`、`reason`に審査理由を指定 |

申請種別は`business_upgrade`、`company_create`、`company_profile_update`。一覧は`page`・`page_size`で取得し、既定20件・最大100件。企業・ユーザーの検索は`q`を使う。ユーザーはメールと表示名、企業は表示名で検索する。

## 移行と検証

既存DBには`000005_user_company_requests.up.sql`を適用する。通常のCompose起動時に`db-migrate`が実行する。既存の有効な担当者紐付けがあるユーザーは業者区分へ移行し、未所属ユーザーは一般区分とする。運用担当者が既存の`auth-link`コマンドで新たに明示的な紐付けを作る場合も業者区分を付ける。既存企業のプロファイルは空欄から管理者が登録できる。

Goの実PostgreSQL統合テストで、申請者の権限・他人のデータへのアクセス拒否、CSRF、重複申請、同時承認、企業・所属・構成の作成、競合、所属再追加、区分変更、セッション失効、監査失敗時のロールバックを検証する。DBテストでは制約と既存データの移行を検証する。フロントエンドのPlaywrightテストはループバック専用のAPI fixtureを使い、一般→業者→企業作成→プロファイル変更の申請と審査結果の表示、管理画面の操作とスマートフォン表示を確認する。

この機能は実APIとDBに保存する。`/preview`内の写真・提出・共有・削除申請などの画面は引き続き開発用の架空データであり、この申請一覧には取り込まない。
