# MobilTracer 要件レビュー用の内容整理

## 資料の概要

目的: 顧客候補と提供側が、共通基盤で三業態の記録業務を扱えるかを確認し、MVPの受入と導入前の未決事項を話し合う。

対象者: レンタカー・販売店・修理業者の業務責任者、MobilTracerの導入・開発・保守担当者。

作成日: 2026-10-25。更新日: 2026-10-30。入力は `design.md` v0.3.0の要件見直し。詳細仕様は要件原本を参照する。この文書は説明内容の整理であり、要件の編集原本を置き換えない。

---

## 車両の状態を、関係者が後から確認できる記録にする

発表資料は、貸出前の傷を利用者が後から示しにくい問題を挙げている。MobilTracerは、状態・整備・修理・引き渡しの記録を残し、同じ内容を関係者へ提示する。顧客は導入事業者、利用者は借受人・購入者・修理依頼者、提供側は構築・保守の主体を指す。

記録の改ざん検証は、登録後の内容変更を検出する。撮影内容の真実性、傷の責任、請求の妥当性や法的な証拠能力を保証しない。

---

## 共通基盤と設定を使い、三業態へ提供する

- 共通基盤: 車両→案件→記録を軸に、記録、比較、提示、回答、検証、追記、共有、監査を扱う。
- 業務モジュール: レンタカーの貸出・返却、販売店の仕入・納車、修理業者の入庫・作業承認・引き渡しを選択する。
- 顧客別設定: 必須項目、撮影箇所、点検、業務段階、承認者、期限、用語、ロゴ等を顧客に合わせる。

顧客ごとのコード複製を基本方式にせず、共通基盤を更新する。設定変更は他社や確定済み記録へ遡及させない。8方向撮影と24時間の異議受付は固定仕様ではない。

## 記録と相手の合意を分けて扱う

担当者が提出した記録版は、相手が署名しなくても保存する。記録・原本は期間経過による自動削除を行わず、個別の削除は理由と承認の経緯を残す。圧縮・アーカイブは別途検討する。閲覧、受領、状態同意、作業承認を分け、回答を特定の版と確認文面へ結びつける。無回答と期限経過は同意にしない。

訂正・補足は元版を残して追記する。業務完了、異議対応、検証基準の登録、照合結果も別々の状態とする。利用者には、提示内容と自分の回答を後から確認する方法を案内する。

## 三業態の最小フローで使い方を確かめる

| 業態 | 代表フロー | 確認する例外 |
| --- | --- | --- |
| レンタカー | 貸出前記録→提示・回答→貸出→返却比較→控え | 署名拒否、燃料・備品差、異議 |
| 販売店 | 仕入・下取記録→整備履歴→選択共有→納車確認 | 過去利用者の個人情報、所有者変更 |
| 修理業者 | 入庫記録→見積承認→作業・追加承認→比較・引き渡し | 未承認の追加作業、見積変更、再確認 |

一人で管理・受付・整備を兼務する顧客も想定する。予約・決済・会計・在庫・部品発注を、これらの流れの成立条件にはしない。

---

## MVPは記録・共有・確認・検証の中核価値を実証する

- 三業態の代表フローを同じ基盤と設定で実行できること。
- 提示内容と回答を利用者が後から確認できること。
- 署名拒否や異議があっても提出記録が残ること。
- 登録済み写真の差し替えを検証で検出できること。
- 顧客設定の変更が他社・確定済み記録に影響しないこと。

AIは基本業務の必須条件としない。動画、大量移行、高度な承認、外部連携等は導入検証後の拡張として扱う。詳しい受入条件は要件定義書のAC-01〜AC-17を参照する。

---

## 導入前に合意する条件を明確にする

| 論点 | レビューで決める内容 |
| --- | --- |
| 本人確認・署名 | 回答者の確認方法、代理回答、受領・同意・作業承認の文面 |
| 検証基盤 | Tapyrus等の採否、鍵・登録先の運用主体、登録失敗時の扱い |
| 保存・共有 | 原本・控え・監査の継続保存、個別削除、所有者変更、事業者間共有 |
| 性能・復旧 | 想定規模、画像・回線条件、応答時間、復旧目標、サポート範囲 |

数値目標は提案であり、実測・顧客合意済みではない。製品実装や受入試験が完了したことを示す説明にはしない。
