構成の承認: この会話の「お願いします」を、18枚の設計からMarp資料・PDFの生成へ進む承認として記録する。製品要件の承認とは分ける。

参照原本: [要件定義書](design.md) v0.3.0。説明上の省略がある場合は要件原本を優先し、この設計書だけで仕様を追加・変更しない。

## 想定する説明と見せ方

対象者は三業態の業務責任者と、提供側の導入・開発・保守担当者。共通基盤で代表業務を扱えるかを確認し、MVPの範囲と導入前に決める事項を話し合う資料とする。

発表時間・枚数は未指定のため、説明15分・18枚を提案する。質疑・合意形成の時間はこの15分に含めない。各ページの時間は説明配分の目安で、実測値ではない。

16:9の横長画面を想定し、文章は1枚3〜5項目を上限とする。図表のpx幅は1920×1080pxで設計した場合の目安とし、生成時の画面寸法に合わせて調整する。図のページは図と短い説明を中心にし、要件原本の長い表をそのまま縮小して載せない。文字サイズの調整より、内容の分割を優先する。

各ページの「伝えること」を、タイトル直下に置く一文のメッセージとして使う。表紙・章扉では副題に反映する。本文や図表はその一文を支える情報として配置する。

表紙・章扉はページ番号を非表示、説明ページは通し番号を表示する。通常ページの下部に参照する要件IDまたは原本の章を短く記す。話者メモには補足と例外を置き、投影する本文と分ける。

### テーマ・図表の方針

`classmethod-marp-theme`の `title`、`section`、`content-image-right`、`column-layout` 等のレイアウトを想定する。CSSの導入と描画確認は次のMarp生成段階で行う。MobilTracerは文字で表記し、未提供の製品ロゴ、Classmethodのロゴ、所属・発表者名を補わない。

図表は記録版、業務段階、公開範囲の関係を示す概念図とする。採用未決のDB・API・チェーン構成を確定した構成図にしない。色に加えて見出しと状態名を使い、未合意・検証待ちを完了色だけで伝えない。図表はMarp生成時に作成し、この段階では配置と内容を定義する。

## スライド詳細

### スライド01: MobilTracer 要件レビュー

- レイアウト: `title`。ページ番号は非表示。
- 伝えること: 三業態で共通基盤を使うための要件をレビューする。
- 投影内容: タイトル「MobilTracer 要件レビュー」、副題「車両の記録・共有・確認・検証」、参照版「要件定義書 v0.3.0」、状態「検討案・顧客承認前」。
- 図表・配置: 中央に製品名と副題。下部に参照版と状態を配置する。ロゴ画像は使わない。
- 話者メモ: 完成した製品の紹介ではなく、対象範囲と受入を確認する資料であることを伝える。
- 原本との対応: 第1章、第2章。

### スライド02: 同じ記録を後から確かめる

- レイアウト: 基本。ページ番号を表示。
- 伝えること: 車両の状態を、片側だけが持つ記録から関係者が確認できる記録へ変える。
- 投影内容: 「預ける前後の状態を残す」「同じ内容を相手へ提示する」「提示内容と回答を後から確認する」の3項目。
- 図表・配置: 本文の下に、顧客＝導入事業者、利用者＝借受人・購入者・修理依頼者、提供側＝構築・保守主体、の用語を3行で配置する。
- 話者メモ: レンタカーの傷を例に説明し、販売・修理にも共通する課題へつなぐ。未再検証の相談件数・請求額は掲載しない。
- 原本との対応: 第2章、第3章。発表資料p.2、4。

### スライド03: 三層で顧客に合わせる

- レイアウト: `content-image-right`。左35%、右65%を目安とする。
- 伝えること: 共通基盤を保ち、業務と顧客設定を組み合わせて提供する。
- 投影内容: 左側に「共通基盤」「業務モジュール」「顧客別設定」の役割を各1文で配置する。
- 図表・配置: 右側に幅約1,050pxの三層図。下段を共通基盤、中段をレンタカー・販売店・修理、上段を項目・撮影・承認・期限の設定とする。
- 話者メモ: 共通する情報の関係は車両→案件→記録。顧客ごとにコードを複製する方式を基本にしない。
- 原本との対応: 第5章、第9章、FR-T01、FR-T02、CON-003。

### スライド04: 設定と追加開発の境界

- レイアウト: `column-layout`。左右2列。
- 伝えること: 顧客要望を、標準・設定・追加モジュール・個別開発のどこで扱うか判断する。
- 投影内容: 左列に「標準：提出版・権限・監査」「設定：撮影箇所・必須項目・承認順」。右列に「追加モジュール：再利用できる業務能力」「個別開発：設定等で表せない顧客固有要件」。
- 図表・配置: 各項目は名称と1例に留める。下部に「8方向撮影・24時間の異議受付は初期設定候補」と一行で表示する。
- 話者メモ: 個別開発の判断には更新追随・保守費用・情報保護を含める。権限分離・提出版保全・未合意表示は設定で解除できない。
- 原本との対応: 第5章、FR-C05、FR-C13、FR-T02、FR-T03。

### スライド06: 署名がなくても記録を残す

- レイアウト: `content-image-right`。左40%、右60%を目安とする。
- 伝えること: 相手の回答に関係なく、提出時点の内容を固定して保存する。
- 投影内容: 「提出版は変更不可」「無回答・拒否でも提出版を保持」「訂正は元版を残して追記」の3項目。
- 図表・配置: 右側に幅約950pxの版の概念図。「下書き→提出v1」の下へ「同意・拒否・未回答」を別の枝で配置し、「訂正→提出v2」はv1を残した関連として示す。
- 話者メモ: v1への署名をv2へ流用しない。相手が署名しないと記録そのものを残せない方式から変更している。
- 原本との対応: FR-C07、FR-C08、FR-C11、AC-03、AC-09。発表資料p.8、11、13との相違。

### スライド07: 確認の意味を分ける

- レイアウト: `column-layout`。左右2列、各列2項目。
- 伝えること: 閲覧・受領・状態同意・作業承認を混同しない。
- 投影内容: 左列に「閲覧：内容を表示した」「受領：記録を受け取った」。右列に「状態同意：提示状態へ同意した」「作業承認：対象作業の実施を認めた」。
- 図表・配置: 四つの名称を同じ強さで示す。下部に「回答は記録版・確認文面・回答者に結びつける」と短く記す。
- 話者メモ: 開封しただけでは明示的な受領回答にならない。受領だけを状態同意にせず、無回答・期限経過を承認に変えない。作業承認は対象範囲・金額と結びつく。
- 原本との対応: FR-C08、FR-M03、AC-02、AC-09。

### スライド08: 完了を一つの状態にしない

- レイアウト: `content-image`。図を中央に配置。
- 伝えること: 業務、記録、回答、異議、検証の状態は併記する。
- 投影内容: 「返却完了／提出済みv2／受領のみ・状態未同意／異議対応中／検証基準登録待ち」の表示例と、「業務完了は、双方同意や登録完了を意味しない」の一文。
- 図表・配置: 幅約1,400pxの状態パネル。業務・記録・回答・異議・検証の五つの行に分け、各行に状態名を表示する。未合意・異議・登録待ちを色だけに頼らず文字で示す。
- 話者メモ: これは状態の説明例であり、実装済み画面のスクリーンショットとして提示しない。
- 原本との対応: 第9章、FR-C10、FR-C13、AC-08。

### スライド09: 検証できる範囲を示す

- レイアウト: `column-layout`。左右2列。
- 伝えること: 登録後の変更の検出と、撮影内容や責任の証明を区別する。
- 投影内容: 左列「照合の対象」、右列「別途の確認が必要」の3行の対比。第1行は「原本と独立基準の比較／撮影内容の真実性」、第2行は「差し替え検出／傷の責任」、第3行は「基準・原本不足時の検証不能／請求の妥当性・法的効力」とする。
- 図表・配置: 3行の左右対比を同じ高さで配置する。下部に「Tapyrusは技術候補。登録状態と照合結果も分ける」と記す。
- 話者メモ: 通常DBの照合値まで変えた場合も、独立基準との不一致を確かめる。写真そのものや直接識別できる個人情報をチェーンへ載せない。
- 原本との対応: FR-C09、FR-C10、NFR-03、NFR-12、AC-04。発表資料p.13。

- 伝えること: 業務は違っても、記録・提示・回答・比較を共通化する。
- 投影内容: 見出しと「貸出・納車・修理の代表フローで確認する」の一文。

### スライド11: 貸出前後の状態を比べる

- レイアウト: `content-image-right`。左40%、右60%を目安とする。
- 伝えること: 貸出前後を同じ箇所で記録・比較し、確認と異議を残す。
- 投影内容: 左側に「状態・燃料・距離・備品を記録」「借受人へ提示して回答」「返却時に比較し、異議も保全」の3項目。
- 図表・配置: 右側に幅約950pxの縦フロー。「貸出前記録→提示・回答→貸出→返却比較→控え」。提示・回答の横に「拒否・未回答でも提出版を保持」の分岐を付ける。
- 話者メモ: 差分だけで責任・請求を決めない。貸出続行の条件は顧客設定・業務判断として確認する。
- 原本との対応: FR-M01、FR-C06、FR-C13、AC-01、AC-03、AC-15。

### スライド12: 選んだ履歴を購入者へ共有

- レイアウト: `content-image-right`。左40%、右60%を目安とする。
- 伝えること: 仕入・整備・納車の履歴を蓄積し、購入者へ必要な範囲を提示する。
- 投影内容: 左側に「仕入・下取時の状態を記録」「整備履歴から共有範囲を選択」「納車版への受領・同意を確認」の3項目。
- 図表・配置: 右側に幅約950pxの縦フロー。「仕入・下取→整備履歴→購入前共有→納車確認」。購入前共有の横に「旧利用者の個人情報は除外」と記す。
- 話者メモ: 共有された履歴だけを車両の全履歴と表示しない。出所不明の履歴も確認済みにしない。
- 原本との対応: FR-M02、FR-C18、AC-01、AC-06。

### スライド13: 承認した作業範囲を残す

- レイアウト: `content-image-right`。左40%、右60%を目安とする。
- 伝えること: 当初見積の承認と、追加作業の承認を別の対象として残す。
- 投影内容: 左側に「入庫時の状態と依頼を記録」「見積の内容・金額を承認」「追加作業は別途承認」の3項目。
- 図表・配置: 右側に幅約950pxの縦フロー。「入庫→見積提示→承認済み範囲の作業→引き渡し」。追加作業の枝に「追加提示→承認待ち→承認済み範囲へ」を置く。
- 話者メモ: 追加承認前の範囲は着手可能な段階へ進めない。見積の内容・金額の変更後は再提示し、内部承認を利用者の作業承認に置き換えない。
- 原本との対応: FR-M03、FR-C08、AC-01、AC-09。

### スライド14: 履歴と公開範囲を分ける

- レイアウト: `content-image-right`。左40%、右60%を目安とする。
- 伝えること: 車両の履歴を引き継ぐことと、過去の個人情報を公開することを分ける。
- 投影内容: 「ナンバー以外の内部識別子で追跡」「所有者変更で自動公開しない」「共有は相手・版・項目・期間で限定」の3項目。
- 図表・配置: 右側に幅約950pxの概念図。蓄積した履歴から「整備事実」だけを選んで新所有者へ渡す矢印を描き、「旧借受人の氏名・連絡先・署名」は公開対象から分けて配置する。
- 話者メモ: 共有取消しは以後の取得へ反映する。既に取得済みの帳票の回収や、無期限の本人控え閲覧を約束しない。
- 原本との対応: FR-C02、FR-C12、FR-C17、FR-C18、AC-06、AC-13。

### スライド15: MVPで確かめる五つの条件

- レイアウト: 基本。ページ番号を表示。
- 伝えること: 記録・共有・確認・検証の中核価値を、五つの必須条件で確かめる。
- 投影内容: 「三業態を共通基盤と設定で実行」「提示内容と回答を後から閲覧」「署名拒否・異議でも提出版を保持」「写真差し替えを検出」「設定変更から他社・確定版を保護」の5項目。
- 図表・配置: 五つの確認項目を上から並べる。未実施の試験にチェックマークや合格印は付けない。
- 話者メモ: 架空データの中核実証だけで、本番導入の承認としない。本人確認、保存、復旧、サポート等の導入条件も原本に従って確認する。対応表の100%は製品試験の合格率ではない。
- 原本との対応: 第11章、第12章、GOAL-001〜GOAL-004、AC-01〜AC-05。

### スライド16: 拡張機能は段階を分ける

- レイアウト: `column-layout`。左右2列。
- 伝えること: 中核実証に必要な範囲と、導入後に選択する拡張を区別する。
- 投影内容: 左列「導入後に検討」に「動画・大量移行、高度な承認・通知、外部連携は導入検証後に選ぶ」の一文。右列「将来の確認支援」に「AIは傷・変化の候補、撮影品質、入力の確認を支援する候補」の一文を配置する。
- 図表・配置: 下部に「AIなしで基本業務を実行。責任・請求の自動決定は対象外」と記す。
- 話者メモ: 予約・決済・会計・在庫・部品発注を自動的にMVPへ含めない。車両以外への適用も将来構想である。
- 原本との対応: 第4章、第11章、FR-T07、FR-A01、CON-001、CON-002。

### スライド17: 導入前に決める四つの条件

- レイアウト: 基本。4行の短い表。
- 伝えること: 本人確認、検証方式、保存・共有、非機能条件を合意して導入へ進む。
